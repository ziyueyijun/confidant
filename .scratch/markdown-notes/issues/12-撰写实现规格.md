# 撰写实现规格

Type: task
Status: open
Blocked by: 02, 03, 04, 05, 06, 07, 08, 09, 10, 11

## Question

把整张地图的结论收敛成一份可交接的 `.scratch/markdown-notes/spec.md`。

这是地图的终点产物。交给实现 agent 之后，它不应该再需要做任何设计决定。

规格须覆盖：

- 产品命题与 MVP 功能边界（含明确的 out of scope 清单）。
- 技术栈与版本：Electron、编辑器内核、构建工具链、关键依赖。
- 进程与模块架构：主进程 / 渲染进程 / preload 的职责划分，IPC 接口清单。
- 数据模型与磁盘契约：库结构、`%APPDATA%` 里存什么、attachments 约定、markdown 规范化规则、frontmatter 与未知语法的处理铁律。
- WYSIWYG 渲染策略：语法标记显隐规则、input rules、各节点类型的处理方式、代码块特例。
- 文件系统行为：自动保存、外部变更、冲突处理、异常情况。
- 搜索的实现方式与交互。
- 界面布局与视觉规范（引用界面布局原型的 asset）。
- 一等验收标准与验证方式：IME 压测清单、round-trip 保真测试、性能基准。
- 实现顺序建议（哪些部分先做能最早跑起来）。

**注意**：这是 `task` 类型，不是 grilling——到这一步不应该还有待决定的事。如果写的过程中发现有未决问题，说明地图还没走完，应该回去补 ticket，而不是在规格里替用户拍板。
