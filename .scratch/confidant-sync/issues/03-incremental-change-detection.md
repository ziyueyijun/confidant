# 03: 增量同步——变更探测

**What to build:** 改一个笔记再点同步，只有它被传上去；在别处（另一台机器、NAS 的文件管理器）改了远端的另一个笔记，同步时只有它被拉下来。没变的文件不重复传输。远端那一侧的判定靠验证符、修改时间与大小三者**任一不同**就下载并算内容 hash 确认——**内容 hash 才是权威，验证符只做变化探测**。

### 判定集中在一处

`packages/sync/lib/change-detect.ts` 的 `remoteEntryChanged(record, entry)`（纯函数，已导出供票 07 启动探测复用）。逐字段规则：

- 两侧都有值 → 不同即「疑似已变」；
- **恰一侧为 null → 算变**（无法确认相同则取保守侧）；
- 两侧都为 null → 不算变（Alist 从不返回验证符，自动退化到「时间 + 大小」）；
- 验证符按**不透明字符串**原样比较，不解析 `W/` 语义、不剥离引号。

决策 35 的「任一不同即下载确认」由此满足；**内容 hash 仍是唯一权威**。

### 最有价值的一条用例（A5）

**验证符没变、内容已变** —— 远端以 `etag: '"FIXED"'` 钉住，内容由 `AAAA` 改为 `BBBB`（同长度），只改修改时间。测试先坐实「etag 与 size 都未变」，再断言仍下载、本地内容变为 `BBBB`。

做了**变异验证**：把 mtime 信号从判定里删掉后 A5 立即失败。这证明该用例真在鉴别行为，不是顺路通过。若引擎只看验证符就跳过，就是静默丢内容。

### 已知弱点（记录在案，非 bug）

**A6：验证符、修改时间、大小三者全等时无法探测远端改动**（Nextcloud「同一秒内覆盖且验证符不变」的极端形态）。要覆盖它只能每次都 GET，增量也就无从谈起。已用显式用例记录，建议票 08 真机复核。

另：D3「服务端忽略 If-Match」是**回归护栏**而非行为差异用例 —— 正确引擎发出的 `If-Match` 总与它上次观测的验证符一致，确定性测试里构造不出差异。正确性来自同步前状态比对 + 上传后回读校验大小（决议 47/48），不来自该头。

### webfake 增补的畸形态

`putFile(path, data, meta?)` 可钉住 etag（强/弱/无引号）与 lastModified；新增 `stat()` / `setEtag()` / `setLastModified()`；新 quirk `ignoreIfMatch`；请求日志补 `ifMatch` / `ifNoneMatch` 头。全部为「只增不减」。

### 未敢确认的假设

1. 「恰一侧为 null ⇒ 算变」是对决议 35 的**保守解读**，规格未明写 null-vs-值的语义。好处是绝不漏内容；代价是服务端中途开始/停止返回某字段时会多一次全量探测（一次后即稳定）。改点：`change-detect.ts` 的 `fieldChanged` 一行。
2. 把 `remoteEntryChanged` 放进公共入口点（理由：它是决议 35 的对外契约，且票 07 需要）。
3. 「不写盘」用本地文件 mtimeMs 相等断言（NTFS 100ns 精度，实测稳定）。
4. **真机服务端行为一概未验证**（绿联 / Nextcloud / Apache 压缩后的验证符形态），全部依据规格 Further Notes 的二手记录构造 —— 归票 08。
