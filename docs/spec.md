## 0. 一页纸

**知己笔记**（`confidant`）是一个本地优先的个人知识管理桌面应用。笔记是用户自己的纯 Markdown 文件；应用提供编辑、检索与同步，但不拥有数据。

- **只服务作者本人**：两台 Windows 机器（例如家与公司），用 WebDAV 在两者之间同步。**只支持 Windows**（macOS 与 Linux 均不支持）。
- **第一原则：笔记文件是唯一真相。** 用任何外部编辑器改文件后应用必须照常工作，索引必须能从文件完全重建。与它冲突的提案一律不作数（[ADR-0003](adr/0003-files-are-the-only-truth.md)）。
- **验收标准是一条使用承诺，不是功能清单**：用两周真实地只用它（§9）。

## 1. 产品的第一性描述

### 给谁

一个人。作者自己，两台 Windows 机器（例如家与公司）。没有账号、没有协作、没有第二个用户。

### 解决什么

**让笔记在「有知识库能力」与「文件完全属于自己」这两件事上不再二选一。**

### 为什么现有工具不够

作者目前同时用两个工具，各自缺一半：

| | 思源笔记 | Typora |
|---|---|---|
| 知识库能力（反向链接、跨笔记检索、块引用） | 有 | **没有** |
| 文件干净、可用外部工具改、可 Git 管理 | **没有**——数据在 `.sy`（JSON）里 | 有 |

- **思源的代价是数据主权**：`.sy` 是自有格式，外部编辑器改不了；导出 Markdown 是单向且有损的（块引用退化成死引用、数据库块丢失）。笔记不完全属于自己。
- **Typora 的代价是没有库**：没有反向链接、没有跨笔记检索。

### 三条具体的「现有工具做不到」

这三条是差异化的全部，也是本项目值得存在的理由：

1. **中文检索开箱即用。** 没有一家做到（Obsidian 官方文档完全不提 CJK，单字搜索 bug 挂了六年未修；社区要靠插件打补丁）。中文用户 100% 的时间在 IME 里写作，而检索是这类软件里用得最多的地方。
2. **数据主权。** 笔记是纯 Markdown 明文，能用 Git 做版本历史、能被任何工具处理、软件不做了也不丢东西。
3. **全库链接自动更新 + 断链检测。** 七家参照产品（Obsidian Sync / remotely-save / Joplin / Syncthing / Dropbox / 坚果云 / Nextcloud）**没有一家做全库链接自动更新**。

## 2. 功能范围

### 2.1 MVP 做什么

**一个界面。** 应用只有一个主界面——左边文件树、中间标签页 + 编辑器、右边大纲、底部状态栏。检索、同步、设置都是它的部件（弹窗或面板），**不是可以切换的几种形态**。

| # | 能力 | 要点 |
|---|---|---|
| 1 | **长文写作** | CodeMirror 6 所见即所得，保留源码视图开关；标签页（含脏点与关闭确认）、可向右分屏 |
| 2 | **检索** | 逐字索引全文检索 + 操作符 + 高亮预览 + 引用的检索（§5） |
| 3 | **链接** | 小节级链接、反向链接面板、断链检测与批量修复（§3.4） |
| 4 | **文件树** | 基于真实文件系统的任意层级嵌套；文件与文件夹同级共存 |
| 5 | **工作空间** | 同一时刻打开一个，可切换；有「最近打开的」列表；首次启动三步向导 |
| 6 | **同步** | 通用标准 WebDAV，双向（§6） |
| 7 | **文件关联** | 出现在「打开方式」里。**应用不提供「设为默认」入口**——用户在 Windows 设置里自己决定 |
| 8 | **自动更新** | 启动时 + 每 24 小时检查；下载完提示用户而非自动重启 |
| 9 | **写盘安全** | 原子写 + 有限重试 + 高风险时刻备份（§7） |

**明确不做**：捕捉、日记、标签系统、收件箱。理由见 §2.2。

### 2.2 明确不做什么

**永不毕业**（在目的地之外）：

- 移动端 / 平板应用
- 多用户协作、共享、评论
- 端到端加密 / 静态加密——与「文件是唯一真相」直接冲突：加密后 Typora 打不开、Git 管不了，而那正是本项目的立身之本
- AI 功能（问答、续写、自动打标签）
- 关系图谱可视化（反向链接**列表**在范围内，图谱不在）
- Linux 支持、macOS 支持
- 代码签名证书（第一版只服务作者本人，未签名的 SmartScreen 警告可接受）
- 坚果云专属兼容与故障规避（只实现标准 WebDAV）
- 发布级产品化：应用商店、面向陌生用户的设计
- **导入器（全部）**——不做从思源 / Obsidian / flomo / Notion 的迁移，库从空开始
- 段落级（块级）链接与块 ID

**明确不做但容易顺手做出来的**（写在这里防止漂移）：

- **捕捉与收件箱**——不做「一键记一句话落到 `inbox.md`」。它不是写作的前置步骤，而是一个需要维护的中间态；用户要记就新建一篇笔记，或直接写进正在写的那篇。
- **日记**——不做「一天一篇按年归档」的特殊目录与入口。日记就是普通笔记，想按日期组织就自己建文件夹。
- **标签系统**——元数据区不再有 `tags` 键的语义，搜索不再有 `tag:` 操作符，不做标签筛选与统计。（**注意**：外部编辑器写进去的 `tags` 字段仍会被原样保留——这是格式契约，与认不认它无关。）
- 不做内置版本历史（推荐把库变成 Git 仓库）
- 不做「一篇笔记同时只允许一台机器编辑」的上锁（理由见 §6.9）
- 不做模糊 / 容错检索（§5.6）
- 不做内置备份的每次保存（§7.3）

### 2.3 一处由本文显式推迟的范围

**数据结构变更的迁移**（将来元数据区 schema 或链接语法变了，已有笔记怎么办）——这是 map 的「Not yet specified」里唯一还悬着的一项，本文把它**显式推迟到 MVP 之后**，理由是它现在无法被设计成一件具体的事：

- 格式契约被刻意设计成**对新增宽容**（元数据区未知字段一律原样保留、链接是纯文本且带转义规则），所以**新增**字段不需要迁移
- 真正需要迁移的是**破坏性变更**，而那种变更在单人自用的场景下可以由一次性的重写脚本解决
- 而破坏性变更目前**没有任何具体的候选**——为一个假想的问题设计迁移机制，只会得到一套没人用的机制

**结论：不进 MVP，不单独立票。** 等真的需要破坏性变更时，那件事本身会定义它需要什么。

## 3. 格式契约

库是**对外承诺的格式契约**——因为承诺了「外部编辑器改文件一切正常」。每一条都通过这个测试：**用 Typora 或记事本按此规范手工建一个文件，回到应用里一切正常。**

### 3.1 库的物理结构

```
<库根>/
├── <笔记>.md                  ← 笔记平铺在库根，用户可自建子目录
├── assets/
│   ├── 001/                   ← 附件，每批 500 个
│   └── 002/
└── .confidant/                ← 配置目录
    ├── config.json            ← 库配置 + 库 UUID
    ├── trash/                 ← 回收站
    └── conflicts/             ← 冲突副本
```

**没有特殊目录。** 笔记就是库里的 Markdown 文件，用户按自己的习惯建文件夹——应用不预设 `journal/`、`inbox.md` 这类位置，也不给它们任何特殊语义。文件树如实反映磁盘结构。

**库的位置：`%USERPROFILE%\知己笔记\`**，即 `app.getPath('home')` 拼接，**不用 `app.getPath('documents')`**。

⚠️ 理由：OneDrive 的「文档文件夹备份」会把 `Documents` 重定向到 `OneDrive\Documents`，于是库会被 OneDrive 与本应用的 WebDAV 客户端**双重同步**，产生冲突副本与半写好的文件——这正是当初决定「内置 WebDAV 客户端、不用网盘挂载」要避免的场景。`Documents` 那个「备份工具默认会扫」的优点与它被 OneDrive 劫持是**同一个特性的两面**。

**首次启动三步向导**：① 选位置（预填 `~\知己笔记\`）→ ② 检测（该目录已有 `.confidant/` = 已有库；有散落 `.md` = 第三方库，提示「会作为笔记导入」；命中 OneDrive 重定向则警告）→ ③ 完成。库路径记在系统 appData。

**三条边界**：

- **程序目录与库目录必须物理分离**——自动更新会替换程序目录，绝不能触碰库。启动时校验（若用户把库建在程序目录内则警告）。
- **库被移动 / 删除**：路径失效时**提示重选**，不自动降级为「无库」状态（避免用户以为笔记丢了）。
- **`.confidant/` 是库的一部分，但不是库本身**——可被删除，删掉只丢配置，不丢笔记。

**`.confidant/` 的内容与归属**：

| 路径 | 内容 | 随库同步？ |
|---|---|---|
| `.confidant/config.json` | 库配置 + 库 UUID | ✅ 是 |
| `.confidant/trash/` | 回收站 | ✅ 是 |
| `.confidant/conflicts/` | 冲突副本 | ✅ 是 |
| 索引缓存 | SQLite 索引 | ❌ **否**——存系统 appData |
| WebDAV 凭据 | 服务器地址 + 用户名 + 密码 | ❌ **否**——存系统侧 |
| 同步锚点 | 「上次同步时远端长什么样」 | ❌ **否**——存系统 appData |

**为什么索引缓存放系统 appData 而不入库**：索引是几十 MB 且随时可重建（全库 rebuild 仅 116ms，实测），放库内会让每次改动都同步几 MB 缓存、计入 WebDAV 流量配额。放库内唯一的好处是跟着走，但重建足够便宜，不值那个代价。

**为什么凭据不入库**：不入 `.confidant/` 的原因是那会跟着同步**上传到它自己要连的那台服务器**——密码躺在远端，逻辑上是循环，且「同步的东西本身在同步」的递归问题再次出现。多库情况下凭据按「服务器地址 + 用户名」存，不按库存——两个库连同一台服务器时共用一份凭据。代价是换电脑或重装要重新输一次密码，对单人使用代价基本为零。

**保留名**：只有 `.confidant` 与 `assets` 两个目录名。用户建了同名文件按普通笔记处理，不报错。

### 3.2 元数据区（frontmatter）

**三个正式键**：

```yaml
---
aliases: [认知失调笔记]
created: 2026-09-25T14:30:22+08:00
pinned: true
---
```

- `aliases` —— 别名，让一篇笔记能被多个名字链接和搜到
- `created` —— **硬理由**：WebDAV 无法设置远端文件时间（已实测），文件系统时间戳在同步后不可靠，所以「何时创建」只能写进文件
- `pinned` —— 置顶

**没有 `tags`。** 应用不认标签（§2.2）——但**外部编辑器写进去的 `tags` 字段会被原样保留**，因为「未知键一律原样保留」这条同样适用于它。应用不认它，不等于可以删它。

**未知键一律原样保留，绝不丢弃、绝不报错。** 没有商量余地——文件是唯一真相，丢掉用户写的任何东西都是数据损失。从 Obsidian 迁来的 `cssclasses`、Claude Code 技能文件的 `name`/`description` 都必须原样留着。

**类型不强制**：除 `aliases` 需能解析成列表外，其余按 YAML 原样对待，不校验类型。

#### ⚠️ 坑一：`---` 开头不等于 frontmatter

笔记正文第一行可能就是 `---`（想画横线）。规则：`---` 之间的内容**先尝试按 YAML 解析，成功才当元数据区，失败则整段当正文**。绝不因解析失败报错或丢内容。

#### ⚠️ 坑二：写入必须「最小改动」（不可妥协）

应用写元数据区时**不能重新序列化整个区块**——那会重排字段顺序、改引号风格、丢 YAML 注释、重排长英文串。

**规则：只做增删改目标键，其余字节原样保留。** 需要的是「保留原文的 YAML 编辑」，不是「解析成对象再序列化」。

**为什么不可妥协**：那些 `SKILL.md` 是 Claude Code 的技能文件，**被改写一个字节都可能导致技能失效**。这是「文件是唯一真相」的极端测试用例——库不该因为应用碰过而有任何变化。

#### ⚠️ 坑三：不主动添加元数据区

笔记**没有**元数据区时，应用**不应主动添加**。只有两种情况才写：

1. 用户在应用里**设置**了别名 / 置顶（用户的操作）
2. 新建笔记时

**用 Typora 建的笔记没有元数据区，应用不该给它加。**

### 3.3 文件名与标题

**禁止字符只有 9 个（半角）**：`\ / : * ? " < > |`，加控制字符（U+0000–U+001F）与保留名（`CON` `PRN` `AUX` `NUL` `COM1`–`COM9` `LPT1`–`LPT9`）。

**⚠️ 冒号是静默数据损坏，不是报错。** 实测：写入含半角冒号的文件名会创建**截断名**，内容进入 **NTFS 备用数据流**——文件管理器看不见、**WebDAV 同步不了**、**内容静默消失且不报错**。且 `a:b` 与 `a` 在目录列表里表现为同一项，会污染基于路径的索引。**因此「绝不写入含非法字符的文件名」不是洁癖，是数据保护。**

**替换表（半角 → 全角）**——实测九种全角对应全部可用：

| 半角 | `:` | `*` | `?` | `\|` | `<` | `>` | `"` | `\` | `/` |
|---|---|---|---|---|---|---|---|---|---|
| **全角** | `：` | `＊` | `？` | `｜` | `＜` | `＞` | `＂` | `＼` | `／` |

中文全角标点本来就全部可用（`《》` `【】` `（）` `——` `、` `。` `；` `：` `？！` `""` `……`）。中文写作本就用全角标点，**替换几乎零损失**（`:` → `：` 视觉上几乎一样）。

**三条硬要求**：

1. **绝不写入**含非法字符的文件名（尤其不能让 `:` 进去）
2. **替换发生时明确提示**：「文件名中的 `:` 已替换为 `：`——Windows 不允许半角冒号」。**必须让用户知道，不能悄悄改。**
3. **扫描时若发现**已存在的非法名文件（拷进来的、同步来的），**警告并给出修复选项**，不能默默当作正常笔记

**超长标题**：实测校准——文件名上限是 **255 个 UTF-16 字符**（约 250 个汉字），不是 85 个。

- **超过 200 字符则截断，并明确提示用户**
- **同时检测库根路径长度**：若库根超过 150 字符，首次启动时警告并建议换位置（留余量给「子目录 + 文件名」）
- **不加短哈希**：250 字标题本身极罕见；加哈希会让文件名变难看。两个长标题截断后同名时，应用检测到重名会提示。

**大小写**：Windows 文件名大小写不敏感（实测：写 `casetest.md` 会**静默覆盖** `CaseTest.md`）。因此**链接目标解析必须走文件系统查找，而非字符串相等**——`[[Note]]` 与 `[[note]]` 指向同一文件。

**附件名远在限制内，不受影响。**

### 3.4 链接

**语法：`[[文件名#小节|显示文本]]`**，三段式，**除文件名外各段可选**：

| 写法 | 含义 |
|---|---|
| `[[文件名]]` | 指向整篇笔记 |
| `[[文件名#小节标题]]` | 指向该笔记中的某个小节 |
| `[[文件名#小节标题\|显示文本]]` | 同上，但正文里显示为「显示文本」 |
| `[[文件名\|显示文本]]` | 指向整篇，显示为别名 |

**解析规则**：`[[` 与 `]]` 之间是链接体；**第一个 `#` 之前是目标文件**，之后是小节标题；**`|` 之后是显示文本**。

**转义规则**：目标或小节标题中若含 `#`、`|`、`[`、`]`、`\`，用 `\` 转义（`\[` = 字面方括号）。

**为什么必须自己定转义规则**：Obsidian 干脆**禁止**链接目标含这些字符（官方原文列了 `# \| ^ : %% [[ ]]`），等于把问题推给用户。本项目面向中文写作，逃不掉。

**链接只到小节级**（标题锚点 `## 标题`），不做段落级。理由见 [ADR-0003](adr/0003-files-are-the-only-truth.md)：Obsidian 的块 ID 官方限定「只能由拉丁字母、数字、短横线组成」——中文做不了块 ID。

**链接的存储形态是纯文本**，索引（反向链接表）可从 Markdown 文件完全重建。

#### 改名的两条不对称规则

| 事件 | 应用的行为 |
|---|---|
| **改文件名** | 应用**负责**更新全库链接 |
| **改小节标题** | 应用**不自动**更新链接——猜错会静默改坏原文，比断链严重 |

#### 断链：检测 + 询问，绝不猜

断链必然发生。呈现形态：

1. **编辑区内**：断链显示为**灰色 + 虚下划线**（区别于正常链接），**点击弹出修复询问**（「找不到 `#参考`，但本文有 `#参考资料`，是它吗？」）
2. **全局断链面板**（与冲突面板同构）：一次列出全库所有断链，可批量处理
3. **反向链接面板里**也标出哪些引用是断的

**主动提示改名**：检测到「某个标题被改、导致 N 个链接断了」时，主动告诉用户并给出批量修复选项。**这不是「猜」**——应用检测到的是**明确的改名事实**（旧标题没了、新标题出现了），然后问用户要不要修，用户确认后才动。

#### 反向链接面板

- 打开一篇笔记，底部 / 侧边列出所有引用它的笔记，**带引用处的上下文**（前后各一句）
- 点击可跳转
- **断链（引用了但目标不存在）单独一组**，也能从这里修

#### 链接与检索的关系

**引用了命中笔记的那些笔记也作为结果出现，但排在直接命中之后并予以标注**（§5.5）。

### 3.5 附件与非 Markdown 文件

**附件按数量分批**：`assets/001/`、`assets/002/`……每批固定 500 个文件，满了开下一个目录。

**为什么不是按时间分**：WebDAV **没有「告诉我哪些文件变了」的接口**，每轮同步必须逐目录 PROPFIND，**一轮同步的请求数 ≈ 库的目录数量**。按日分会达 3650 个目录，慢到不可用。按数量分批在两个维度上同时最优：单目录永不超限，且目录总数比按月分还少（一万个附件 = 20 个目录），且不受时间分布影响。

代价：目录名不可读（`001` 而非 `2026-09`）。对附件几乎无影响——用户通过笔记里的链接打开图片，不翻附件目录。

**命名**：时间戳命名（已定）。具体格式由实现定，只需满足「时间戳 + 同一秒内不重名」，例如 `<YYYYMMDD>-<HHMMSS>-<4位随机小写十六进制>.<ext>`。

**引用**：标准相对路径 `![](assets/003/<附件文件名>.png)`（Typora / Obsidian 均能渲染）。

**目录规则只影响新建文件**，已有文件路径永不变——不是不可逆的决定。

**非 Markdown 文件（`.txt` / `.pdf` / `.canvas` 等）**：

| 维度 | 行为 |
|---|---|
| 索引 | **只索引 `.md`**。其它文件不出现在搜索结果里 |
| 文件树 | **出现在文件树里**（能看到、能点开） |
| 同步 | **照常同步**，是库的一部分 |
| 打开 | `.md` 用内置编辑器；其它文件**用系统默认程序打开** |
| 引用 | 图片在编辑器里显示；非图片附件显示为可点链接 |

原则：**应用不假装能处理它处理不了的东西**——不试图编辑 PDF，也不把它们藏起来。

### 3.6 没有特殊目录

库的物理结构到此为止：**笔记 + `assets/` + `.confidant/`**。应用不预设任何「特殊位置」——

- 没有 `journal/`。日记就是普通笔记，想按日期组织就自己建文件夹，文件树会如实显示。
- 没有 `inbox.md`。没有捕捉，也就没有收件箱这个中间态。
- 没有「保留名」。除了 `.confidant` 与 `assets` 两个目录名（应用自己要占），用户建什么都按普通笔记处理。

**这条为什么重要**：特殊目录一旦存在，应用就必须给它特殊语义（自动归档、自动整理、排除索引……），而那些语义用户看不见、改不了、也没要求过。**文件树如实反映磁盘，这是「文件是唯一真相」在目录层面的样子。**

## 4. 技术架构

### 4.1 技术栈

| 层 | 选型 | ADR |
|---|---|---|
| 桌面壳 | **Electron**（版本下限 ≥ 41） | [0001](adr/0001-electron-over-tauri.md) |
| 编辑器内核 | **CodeMirror 6** | [0002](adr/0002-codemirror-over-prosemirror.md) |
| 语言与 UI | TypeScript + React + Vite + Tailwind + shadcn/ui | — |
| 状态管理 | **Zustand** | — |
| 校验 | **Zod** | — |
| 索引 | better-sqlite3（WAL 模式） | [0004](adr/0004-per-character-index.md) |
| 打包 | electron-builder + NSIS per-user | [0005](adr/0005-nsis-per-user-unsigned.md) |
| IPC | 手写 `contextBridge` 白名单 | [0007](adr/0007-hand-written-ipc.md) |
| 测试 | Vitest（**端到端先不做**） | — |
| lint / format | ESLint + Prettier | — |

**为什么 Electron 而不是 Tauri**（这条最容易被将来的自己质疑，因为 Tauri 包小一个数量级）：Tauri 有一个直接命中笔记软件核心场景的**未修复 bug**——Windows 上聚焦**已有内容**的编辑器时 WebView2 冻结 Windows TSF，**中文输入法打不开候选窗、按键被吞**，所有已知 workaround 均无效。即「打开一篇旧笔记继续写」会坏掉。另有一个结构性风险：tao 的 Windows IME 死锁修复已合入 0.36，但 Tauri 2 稳定线锁在 `tao ^0.35` 拿不到。

**为什么 CodeMirror 6 而不是 ProseMirror / TipTap**：后者有自己的一套 JSON 文档树，界面上编辑的是那棵树，需要序列化回 Markdown 才能存盘——于是必然存在「文件里的文本」与「编辑器里的文档」两个状态，而反向解析是**有损**的。那正是本项目要躲开的东西。

**为什么手写 IPC 而不是 `electron-trpc`**：该方案的主流实现（402 stars）最新发版是 2024-12-07，已近两年停更。手写方案的唯一真问题是「类型声明可能与实现脱节」，而**在 IPC 边界用 Zod 校验同时挡住了运行时数据**，比编译期保证更实在。

### 4.2 进程模型

```
┌─────────────────────┐         ┌──────────────────────┐
│   主进程 (main)      │  IPC    │  渲染进程 (renderer)  │
│                     │◄───────►│                      │
│  · 窗口管理          │  context│  · React 界面        │
│  · 文件系统读写       │  Bridge │  · CodeMirror 编辑器 │
│  · SQLite 索引       │  白名单  │  · Zustand stores    │
│  · 文件监听          │  + Zod  │                      │
│  · WebDAV 同步       │  校验   │  ✗ 不能直接碰文件系统 │
│  · 自动更新          │         │  ✗ 不能 import main/ │
└─────────────────────┘         └──────────────────────┘
```

**索引跑在主进程直接读写 SQLite**，理由：Electron 主进程 ≠ UI（UI 在渲染进程，主进程卡住时界面照样能画），真正的风险只是「主进程忙时所有 IPC 请求排队」。而实测显示**全库索引重建只要 116ms**，真正慢的是读文件，而这件事**可以分批做**——每批处理少量文件就交还控制权，让 IPC 请求插进来。

**退路（留到实现时判断）**：若发现某操作在 Node 里天然同步阻塞、分批做不到，则退到 worker 线程。**已实测 better-sqlite3 在 worker 线程可用**，所以退路是通的。

### 4.3 代码组织

```
src/
├── main/             主进程
│   ├── index.ts
│   ├── ipc/          IPC 方法实现 + Zod schema
│   ├── index-db/     SQLite 索引
│   └── sync/         WebDAV 同步
├── renderer/         渲染进程
│   ├── main.tsx
│   ├── components/   UI 组件
│   ├── features/     按功能分（编辑器、搜索、冲突面板）
│   └── store/        Zustand stores
├── preload/          contextBridge 白名单（唯一的桥）
└── shared/           两边都用的：类型、Zod schema、纯函数
```

**三条硬约束**：

1. **`shared/` 只放「两边都真的需要」的东西**——类型、schema、纯函数（如文件名规范化规则）。**绝不放业务逻辑**，否则会变成两边都依赖、谁都能改的垃圾场。**这是这类项目最常见的腐化方式。**
2. **`preload/` 是唯一的桥**，且只做转发，不放逻辑。
3. **`renderer/` 绝不能 import `main/` 里的任何东西**——那是跨进程的假象，实际会在渲染进程里跑主进程代码。

### 4.4 状态管理

**Zustand**，一条判据：**能推导出来的不进 store**（存两份必然不同步）。

| 进 store | 不进 store |
|---|---|
| 当前库路径 | 笔记正文（从路径查） |
| 当前打开的笔记路径 | 编辑器内容（CodeMirror 自管） |
| 搜索结果 | 组件内部临时状态（输入框内容、下拉展开） |
| 同步状态 | |
| 冲突列表 | |
| 界面偏好（主题、侧边栏宽度） | |

**不装路由库**——笔记应用是「单窗口」而非多页面，视图切换用简单状态（`view: 'notes' | 'search' | 'settings'`）。React Router 是为浏览器历史 / URL 设计的，此处没有对应物。

### 4.5 文件监听与编辑竞争

**文件监听：`fs.watch({recursive: true})`，不用 chokidar。** 实测 Windows 上递归监听可用且能捕获深层改动，Node 原生足够，省一个依赖。

**外部编辑 vs 应用内编辑：比对内容哈希（确定性判断）。**

场景：应用内正在编辑《周记》，同时该文件在 Typora 里也被打开并保存了。文件监听器通知应用，应用必须判断这个变化是「我自己写的」还是「外人改的」——**判断错的后果是光标跳动或内容闪回**。

机制：应用记住「我最后写进去的内容的哈希」；文件变化时先算哈希：

- **与我最后写的一致** → 我自己写的，忽略
- **不一致** → 外部改动，走正常处理流程

**为什么不用其它方案**：

- **时间窗口猜**：不可靠——Typora 可能延迟保存、用户可能手快、系统时钟可能偏移。**猜错就是正在编辑的内容被覆盖。**
- **文件锁 / 独占打开**：会**阻止用户在 Typora 里打开文件**，直接违背第一原则。

**配套**：即使判定为「外部改动」，也**不直接覆盖编辑缓冲**——走 §6.5 的挂起机制。

### 4.6 首次打开大库

**立即显示界面 + 进度逐步出现**（显示「已载入 1200 / 3000」），搜索功能显示「索引构建中」。

**为什么不选懒加载**：**搜索会漏**——搜一个词只搜了已索引部分，会得到**错误**的结果。这比等待更糟。

**必须可见的**：进度（已载入 N / 总数）；构建中时搜索不可用，或明确标注结果不完整。

### 4.7 索引与反向链接图

**反向链接图与索引一起建**。理由：链接图的构建本质上就是遍历所有文件的链接，而索引阶段**已经做了一半**（索引要解析每篇笔记内容，顺手就能提取链接）。分开做等于把文件读两遍。

且反向链接面板要「一次列出全库所有断链」，那本来就需要全库的图。

### 4.8 IPC 边界

- 渲染进程**不能**直接碰文件系统——只能调用主进程明确暴露的方法。这既是 Electron 安全模型的要求，也刚好契合本项目：**所有文件操作都必须经过索引层**，于是「索引与文件一致性」只需在一个地方维护。
- `shared/` 放一份接口定义（含 Zod schema），主进程实现并据此校验，渲染进程从 schema 推导类型。
- **数据库：WAL 模式**，且**写操作串行化在一处**（实测确认单写者语义仍在，并发写会 `SQLITE_BUSY`）。

**Zod 用在两处，失败处理截然不同——这个区别是关键**：

| 位置 | 校验失败时 |
|---|---|
| **元数据区解析** | **绝不报错、绝不阻止打开笔记**。未知字段原样保留；校验失败只影响能否使用那些字段（如 `tags` 不是列表就当没有标签），**不影响笔记能否打开** |
| **IPC 边界** | **明确报错**——这是 bug，意味着两边代码不一致 |

**前者是「用户的文件可能长任何样子」，后者是「我自己的代码可能写错了」。**

### 4.9 首次启动引导与多库

**同一时刻一个库，但可切换**，有「最近打开的库」列表。

理由：`.confidant/` 在库内这个设计天然支持切换（每个库带着自己的配置走）；体验上与「永远一个库」几乎无差别，但真想切时有路可走。

**库路径持久化在系统 appData。**

## 5. 检索方案

### 5.1 分词路线：逐字索引

**把每个汉字前后插空格后用 FTS5 `unicode61` 建索引**，查询时以相邻字短语匹配等价于精确子串匹配：

```js
const perchar = s => s.replace(/([㐀-鿿豈-﫿])/g, ' $1 ')
                      .replace(/ {2,}/g, ' ').trim();
// "科学家研究科学" -> "科 学 家 研 究 科 学"
```

于是 `MATCH '"知 识"'` = 相邻字短语 = **精确子串匹配**。

**⚠️ 空格要插在汉字前后，不能只插后面**——只插后面时 `26个` 会粘连成一个 token，导致搜「个大」漏召回（实测踩到并修正）。

**为什么不是预分词**（这条推翻了本可预期的方案，见 [ADR-0004](adr/0004-per-character-index.md)）：实测（100 万字中文语料）预分词方案的单字查询召回仅 **27%**、跨词子串 **31%**（搜「共和」丢 94%），且精度与召回不可兼得。逐字方案**全部类别 100% 召回 / 100% 精确**（783 个随机探针零假阴零假阳）。

关键的意外发现：`wangfenjin/simple` 那个看似复杂的 C++ 分词扩展，**本质就是逐字建 token（+拼音），不是词级分词**——所以能用一行纯 JS 正则复刻，**零依赖**。这也规避了整个行业的通病：**没有分词器，就没有「分词器参数固化在 schema 里、升级要重建索引」的问题**。

**实测数字（100 万字档）**：

| 项 | 值 |
|---|---|
| 索引体积 | 13.99 MiB（**5.18×**） |
| 建索引 | 374ms |
| 单篇增量编辑 | 0.232ms |
| 全库 rebuild | **116.3ms** |
| 查询延迟 | 单字 5.2ms / 2字 1.8ms / 跨词 2.3ms / 短语 0.3ms |
| 召回 / 精确 | **全部类别 100% / 100%** |

**全库 rebuild 只要 116ms 的含义**：「必须做增量索引」的架构压力消失。即使每次都全量 rebuild，百万字库也在 120ms 内完成。

### 5.2 精确性依赖 refine

**逐字索引本身零假阴**——中文子串**一定**能命中（子串 = 相邻的字 = 相邻的 token）。**假阳全部来自「标点被 unicode61 丢弃」**（实测样本：`开会议，决定` 里的「议，决」被当成「议决」）。

**refine（回查原文 `includes`）100% 消除假阳**，代价就是那几毫秒。实测：refine 前 732/783（93.5%，90 个假阳），refine 后 **783/783（100%）**。

**⚠️ 高亮必须自己在 `raw` 列上算。** FTS5 的 `snippet()` / `highlight()` 作用在插了空格的 `seg` 列上——直接用会返回「科 学 家」而非「科学家」。解法：refine 本来就要回查原文，顺手可算出高亮区间。**这不是决策，是实现时必须记住的约束。**

**索引与原文必须同时可用**——refine 要读原文列。这符合「文件是唯一真相」（原文列可从 Markdown 重建）。

### 5.3 简繁互搜：进 v1

**做法：索引时把文本归一化为简体（存进 `seg` 列），查询时也归一化。** 于是「歷史」与「历史」在索引里是同一个东西，**索引体积一点不涨、不需双写**。

**原文列仍存原文**——用户看到的、复制出来的还是自己写的繁体字。归一化只发生在搜索用的那一列。

**唯一的正确性要求**：**refine 回查原文时也要归一化**，否则「搜繁体、原文是简体」会被 refine 误判成假阳。

**依赖**：`OpenCC`（词典驱动，有 Node 绑定）。

**为什么值得**：这是**唯一一个「成本近乎零、而竞品几乎都没做」的差异化点**。

### 5.4 拼音：只索引标题

**打 `zs` 能命中标题为「知识管理」的笔记；正文里的拼音不建索引。**

**理由**：**拼音检索的真实用途是「快速跳转」，不是「全文搜索」。** 用户打拼音时，脑子里已经知道要找哪篇——那是快速切换器的场景。而「记得正文里提过某概念但忘了哪篇」时，人会打汉字。

**索引膨胀被控制在极小范围**：标题很短（几十字），全库标题总量约为正文的百分之一。

**为什么不选全文拼音**：每个汉字要多产出全拼 + 首字母两组 token，**索引膨胀 2–3 倍**。逐字方案已付 5.18×，再加拼音到 10–15×。代价与收益不成比例。

**技术选型**：`pinyin-pro`，准确率 99.846%，gzip 157KB，纯 JS。

### 5.5 排序、语法与触发时机

**排序：标题命中 > 正文命中 > 引用了命中笔记的。**

- 标题命中通常意味着「就是它」，正文命中是「提到过」
- 第三档是**反向链接的检索形态**——「我搜这个词，能把所有相关的东西带出来，包括我没直接写这个词但引用了它的」。混排会污染结果；完全不出现则浪费了已有数据。

**搜索语法（操作符体系）**：

| 写法 | 含义 |
|---|---|
| `知识管理` | 搜正文与标题 |
| `"知识管理"` | 短语（必须连在一起） |
| `知识 管理` | 两个词都要有（AND） |
| `path:技术/待整理` | 限定路径 |
| `title:周记` | **只搜标题** |
| `-path:草稿` | 排除 |
| `知识 path:技术` | 组合 |

**没有 `tag:`。** 应用不认标签（§2.2），所以没有这个操作符。

**为什么不做纯筛选器**：**筛选器点起来比打字慢**，而搜索框是这类软件里用得最多的地方——能用键盘解决的事不该强迫用户换鼠标。

**⚠️ 配套规则：语法错误不报错，按字面搜索。** 打 `tag:读书` 而应用不认这个操作符时，当作「搜 `tag:读书` 这几个字符」——因为用户**可能真的在找含这些字符的笔记**（比如正在写一篇讲标签系统的笔记）。报错会打断用户。

**触发时机：边打边搜，防抖约 100ms。**

理由：实测延迟给了充足余量（单字 5.2ms、短语 0.3ms），即使加上 refine 与 UI 渲染也完全跑得动。而**搜索是最高频操作**，多按一次回车是每天都在付出的税。

**大库保险**：若某次查询超过约 200ms（命中集极大时），显示「搜索中」并允许取消，不让界面卡住。

### 5.6 明确不做

**模糊 / 容错匹配不进 v1。**

理由：**打错字搜不到时，人会立刻重打一遍**——这是本能反应，不需要软件代劳。而容错匹配的风险是**返回一堆不相关的东西**，比「没搜到」更让人困惑（搜「知织」得到一堆含「知识」和「组织」的笔记，无从分辨哪个是哪个）。

技术事实：FTS5 **原生没有模糊匹配**；trigram 只能做子串且对 2 字查询结构性失败。

**也否决了「零结果时降级」**——它看似聪明，但**同一句话在不同时候有不同搜索语义**，用户无法建立稳定预期。

## 6. 同步方案

### 6.1 范围与形态

**双向同步**，**通用标准 WebDAV**，由应用内置客户端实现。

**明确不做坚果云专属兼容。** 坚果云有三条硬限制且官方不打算修：单次请求 750 项、免费版 600 请求/30 分钟、以及最要命的**超限时静默截断结果**（故障模式：同步引擎误判文件不存在，每次同步重新上传上百个文件）。

**但这不等于可以不考虑请求数与目录规模**——标准 WebDAV 服务端也各有上限。这就是 §3.1 与 §3.5 里目录结构的由来。

### 6.2 三条决定方案形状的硬事实

1. **WebDAV 没有设置远端 mtime 的标准方法。** 上传后本地 mtime ≠ 远端 mtime。因此**任何「谁的时间戳大谁就新」的判断都会在上传后立刻误判**。
2. **ETag 不能当内容指纹。** 各家语义不一致（Nextcloud 是 `md5(mtime + inode + dev + size)`），且**没有一家参照产品在同步决策里用 ETag**（Joplin 源码注释：`in practice it's not accurate enough and can lead to conflicts`）。
3. **没有变更日志 API。** RFC 6578 的 sync-collection 在**文件类目录上几乎无人实现**。所以只能 PROPFIND 拉目录 + 比对，**删除检测必须靠「远端清单与上次记录的清单求差集」**。

**综合：判定依据是「本地内容哈希清单 + 远端 `getlastmodified`」的混合策略**——本地算哈希免费，远端必须 GET 全文会撞流量。

### 6.3 同步锚点

**锚点 = `path → 内容哈希` + 上次同步时的远端属性**，存**系统 appData**，**不放库里**。

**为什么不放库**：锚点天然是每台机器独有的（记录「**这台机器**上次看到的远端是什么样」），放进库会同步给另一台、互相覆盖，逻辑上就是错的。库 UUID 存 `.confidant/config.json`，库被移动后锚点仍认得出。

**锚点的性质：可丢弃但不可重建。**

- 删掉它不丢内容（所以它不是真相）
- 但远端只有「当前长什么样」，没有「上次长什么样」，丢失的是**归因信息**
- 后果：**所有文件被判为冲突**

**契约三条**：

1. **锚点丢失 → 强制保守全量对账**
2. **锚点丢失 → 绝不传播删除**
3. 用内容哈希让锚点可退化（混合策略）

### 6.4 触发时机

| 方式 | 语义 | 触发 |
|---|---|---|
| **自动同步** | 合并 | 应用启动时 / 定时（**默认 10 分钟，可配置**）/ 本地有一批改动后（防抖） |
| **「同步」按钮** | 合并 | 手动，与自动同步走同一条路径 |
| **「上传」按钮** | **以本地为准** | 手动，**覆盖远端** |
| **「下载」按钮** | **以远端为准** | 手动，**覆盖本地** |

**自动同步可整体开关。**

**频率为何不能更密**：每轮全量对账的请求数 **≈ 库的目录数量**。

#### ⚠️ 两套语义不能混

上传与下载是**破坏性操作**，界面上必须让这个区别无法被误解。若把三个按钮平铺成同一种样子，用户会以为「上传」也是安全的合并——**那就会丢数据**。

**上传 / 下载必须带确认**：执行前显示影响范围（「将覆盖远端 N 个文件」），并在执行前**自动落一份快照**（进 `.confidant/trash/` 或冲突目录），保证可恢复。

（这三个按钮与 §6.6 首次同步的三个选项是同一种决策——以哪边为准——所以共用同一套确认与快照机制。）

### 6.5 冲突处理

**策略：自动三方合并，失败落副本。**

两边都改了同一篇时，先尝试自动合并；合并成功则静默写回两侧；**合不干净才落副本**。最坏情况与「一律落副本」相同，多数时候省事。

#### 降级链（必需品，不是可选优化）

**必须接受的实测事实**：`node-diff3` 在「两端各追加一行」「一端删相邻行、另一端改别处」「同一行内不重叠的修改」**全部误报冲突**；中文笔记中「一个标题下就是一整段无换行的话」极常见，行级对比看不到段落内部差异，**这种情况必定误报**。

```
行级 node-diff3（必须显式 stringSeparator: /\n/）
    ↓ 不干净
字符级合并（针对「整段无换行」的中文长段落）
    ↓ 仍不干净
落副本
```

**⚠️ `node-diff3` 默认按空白切分，会把中文切碎——必须显式传 `stringSeparator: /\n/`。** 这是使用这个库的硬性前提。

**⚠️ 选库警告**：npm 上 `merge`（3.2M 周下载）是**对象递归合并**不是文本合并，`diff3`（1.2M 周下载）是 0.0.4 老包。**真正能用的是 `node-diff3`（200K 周下载）**。别被下载量误导。

#### 安全阀（本项目设计，非照抄）

**自动合并的结果在写回之前必须校验它同时包含两侧的所有行；不满足则不许静默写回，直接降级落副本。**

Joplin 与 Obsidian 都承认自动合并会出错（官方口径：`may sometimes create duplicate text or formatting problems` / `In rare cases, automatic merging may result in duplicated content`），但**都没有这道校验**。

#### 冲突副本

**放 `.confidant/conflicts/`，不跟原文放同一目录。**

理由（横向对比的两条推论）：

1. **七家里只有 Joplin 做到了「自动合并 + 冲突可见」的闭环，而它恰恰也是唯一不把副本扔进文件系统的一家。** 其余六家全扔在同一文件夹，全无闭环。
2. **「扔进用户会翻的文件夹」≠「用户会处理它」**——坚果云需专门做批量处理工具、Dropbox 让人自己翻、Syncthing 默认只留 10 个（因为会堆积到失控）。

选 `.confidant/conflicts/` 的额外好处：**索引天然干净**，无需写任何「排除索引 / 排除链接补全 / 排除标签统计」的逻辑。若选「跟原文放一起」，这些逻辑全都得写，而它们只是为了解决一个面板本来就能解决的问题。

**副本仍是真实的 `.md` 文件**（不是数据库记录），可用记事本直接打开——符合「文件是唯一真相」。

**命名约束**（三条，具体格式由实现定）：

1. **后缀只用小写 ASCII**——WebDAV 服务端可能是 Linux（大小写敏感），而本地是 Windows（不敏感），混用会造成「本地能建、远端冲突」。**扩展名必须留在末尾**（`笔记.conflict-….md` 而非 `笔记.md.conflict-…`），否则副本不再被当作 Markdown。
2. **含时间戳**，便于排序与人工识别
3. **含机器标识**，便于判断副本来自哪一台

参考格式：`<原文件名>.conflict-<YYYYMMDD>-<HHMMSS>-<机器短名>.md`

**冲突面板是必需品**：应用内一处列出全部待处理副本，每条带「保留我的」「保留远端的」「手工合并」动作，处理完消失，需能并排看两份内容。

#### 正在编辑时远端更新到达

**挂起该文件的同步，停手后再应用。**

不碰编辑缓冲。机制：某文件敲字后的 N 秒内**挂起该文件的同步**；期间远端变化只进角落提示，不进缓冲。等停手 N 秒或切走后再应用，**应用后可按 Ctrl+Z 撤销**。N 待实现时调（倾向 3 秒）。

理由：编辑缓冲里装着**尚未写完的内容**，是全应用最不能被打扰的状态。

**调研未覆盖此项**——这是本项目自己的设计，无横向先例。

#### 二进制文件

**同样走本策略，但二进制不存 base**（无法三方合并），冲突时**直接落副本**。

### 6.6 首次同步

**绝不自动合并两个独立的库。** 四种情况分开处理：

| 情形 | 行为 |
|---|---|
| 远端空 | 只推送 |
| 本地空 | 只拉取 |
| 两边都有、内容一致 | 只记锚点，不做任何操作 |
| **两边都有、内容不同** | **停下来问用户**，不猜 |

第四种情况弹出明确选项：「以本地为准（覆盖远端）」/「以远端为准（覆盖本地）」/「两边合并（可能产生大量冲突副本）」。

理由：这是「**最难的场景，且它必然发生一次**」（此时**没有任何锚点**）。旁证：Joplin 连「远端时间在未来」这种时钟偏移都直接抛错，注释写 `There's currently no automatic fix for this`——业界对无法判断的场景倾向停下来而非猜测。

### 6.7 删除传播

**四种情况分开，并加一道批量闸**：

| 情形 | 行为 |
|---|---|
| 远端删了、本地没动 | 本地也删，**先进 `.confidant/trash/`**（不是真删） |
| 本地删了、远端没动 | 远端也删，但本地**同步日志记一笔** |
| 一边删了、另一边改了 | **绝不自动决定**：保留被改的那份 + 落副本标为待处理（同 Syncthing） |
| **锚点丢失时** | **绝不传播任何删除** |

**批量删除闸**：一次同步若要删 **超过 10 篇**，先停下问用户。阈值可配置。

理由（不是假想风险，是实际事故）：remotely-save 的 `design.md` 把 `deletion protection (blocking)` 列为**必须项**（撞过坑才写上去）；Joplin 有 `deleteChildren: false` + `ignored` 计数 + `updateReport` 诊断，**并有 issue 指向「同步随机删除了所有笔记」**；调研总结的产品教训原话：同步目标上「**一次错误的 stat 会导致大规模误删**」。

### 6.8 重命名识别

WebDAV 无文件持久 ID，改名在协议层是「删 + 建」。

**用内容哈希匹配识别**：内容同、路径变 = 改名，跟着改名并更新链接；内容也变了则无法识别，只能当删 + 建。**协议限制，接受。**

### 6.9 明确不做的「上锁」

**否决「一篇笔记同时只允许一台机器编辑」**，三条理由：

1. **锁不住外部编辑器**——第一原则允许任何编辑器改文件，锁在 Typora 面前无效。**假的安全感比没有锁更糟。**
2. **离线时锁不存在**——锁要求对端先看到它，而两台机器并非一直联网。
3. **锁会卡死**——持有方崩溃 / 断电 / 断网后锁不释放，需做「超时失效」，这是比冲突处理本身更难的分布式问题。

**记入「以后可加」**：其有价值形态不是「禁止编辑」而是**提示**（「注意，另一台电脑刚改过这篇」）——便宜、不卡死、不假装安全。

### 6.10 同步跑在哪

**倾向主进程，与索引同侧**——避免跨进程协调。这条在架构票里是**倾向而非定论**（架构票明确把它留给了同步相关的票），实现时若发现同步阻塞主进程影响 IPC 响应，可退到 worker 线程（已实测 better-sqlite3 在 worker 线程可用）。

## 7. 数据安全

> 「文件是唯一真相」意味着**应用把文件写坏了就是数据丢失**，没有任何数据库可以兜底。本节的目标是**在任何单点故障下都不丢用户的字**。

### 7.1 原子写三步

```
写临时文件  →  fsync  →  rename 覆盖
```

**实测确认 Windows 上 rename 可覆盖已存在文件**（Node 用 `MoveFileEx` + `MOVEFILE_REPLACE_EXISTING`），因此 POSIX 的原子写语义成立。fsync 每次多约 1.3ms，可接受。

**⚠️ fsync 不可省**：实测未 fsync 时数据可能仍在页缓存——**进程崩溃不丢，断电可能丢**。rename 之前必须先 fsync 临时文件，否则「原子写」不成立。

### 7.2 崩溃自愈

**不加「写入完成」标记文件。**

理由：**原子写已经解决了这个问题**——rename 是操作系统级原子操作，**磁盘上永远不会出现半截的目标文件**，崩溃后残留的只有临时文件。加标记文件本身也可能写一半，是无限递归的问题。

**要做的只有一件事**：启动时扫描并删除 `.confidant/` 下的残留临时文件。

### 7.3 备份：只在高风险时刻

**不每次保存都备份，只在「应用要用内存副本覆盖磁盘上外来更新」时备份。**

理由：

- **不备份的问题是真的**——原子写只保证「不是半截内容」，不保证「内容是你要的」
- **每次备份的成本失控**——编辑器自动保存频繁，`.confidant/backup/` 会迅速膨胀到几万文件，**且要跟着 WebDAV 同步上去**（流量配额）
- **瞄准真风险点**：正常编辑保存写的就是用户屏幕上的内容，没有「写错」的可能；危险的是**应用用自己内存里的版本覆盖了磁盘上别处来的更新**

**已有的兜底**：用户可把库变成 Git 仓库，版本历史由 Git 管，优于内置备份。

### 7.4 写入失败

**后台自动重试约 3 次**（间隔 100ms / 300ms / 1s），仍失败则明确报错。

理由：这类占用**绝大多数是瞬时的**（杀毒扫描几百毫秒结束），立刻弹错会让用户以为出了问题。但重试必须有限度。

**关键要求（不可妥协）**：

- **最终失败时，用户的编辑内容必须还在**——不能关掉编辑器丢掉内容
- 界面明确显示**「未保存」**
- 提供**「重试」**与**「另存为副本」**两个出路
- **绝不能假装保存成功**

### 7.5 不预检

- **不预检磁盘空间**——预检与写入之间存在竞态，没有意义
- **不预检可写性**——实测 Windows 上 `chmod` 不进 ACL，「先检查是否可写」不可靠

**直接写、捕获失败。** 错误处理必须区分错误码：`ENOENT`（目录 / 文件已不存在，竞态）、`EISDIR`（把目录当文件）、`EPERM`（被占用或无权限）、`ENOSPC`（磁盘满）。

### 7.6 外部删除与改名

**已确认的边界**：**外部删除不进 `.confidant/trash/`**——那是操作系统的事，应用不该假装能撤销你（或别的程序）的删除。但**要记进同步日志**，这样在别处仍能查到「这篇是什么时候没的」。

**行为**：

- **没在编辑的** → 悄悄更新列表（这是「如实反映」）
- **正在编辑的那篇被外部删除或改动** → **必须提示**（直接影响用户手上的工作）

**为什么不每条都提示**：用户在 Typora 里批量整理一次，应用会弹二十个提示——噪音太大。

### 7.7 超大文件与超长行：两道独立防御

**① 文件体积：超过 5MB 不索引**

- 5MB 纯文本 ≈ 250 万汉字（一本《红楼梦》约 70 万字），远超任何正常笔记
- 超限行为：**不索引**（不出现在搜索里）、**仍在文件树里显示**、双击用系统程序打开、**界面标注「文件过大，未索引」**

**② 单行长度：某行超过 10000 字符则索引时截断该行**

- **不影响用户看到完整内容**，只影响那一行能否被搜到

**为什么两道都需要（实测依据）**：构造的「50MB」文件实际 153.9MB，`readFileSync` 只花 823ms，但**按 `\n` 分割后只有 1 行**——逐字索引会面对**一个 5130 万字符的超长 token 序列**，可能卡死或吃光内存。文件体积限制能拦住这种情况，但 4MB 的单行文件同样危险——所以两者是独立的防御。

**二进制判据**：**内容含 NUL 字节（`0x00`）即视为二进制** → 跳过索引，但在文件树中显示。

### 7.8 回收站

`.confidant/trash/`，存放**应用内删除**的笔记，可还原。

**外部删除不进回收站**——在文件管理器或其他程序里的删除由操作系统负责，应用不假装能撤销它。

## 8. 界面

> **只有一个界面**：左边文件树、中间标签页 + 编辑器（可向右分屏）、右边大纲、底部状态栏。检索、同步、设置都是它的部件，不是可切换的几种形态。

### 8.1 已验证的实现路径

| 能力 | 实现路径 | 状态 |
|---|---|---|

| 大纲 | 正则提取 H1/H2/H3，点击跳转（`useImperativeHandle` 暴露 `scrollToLine`） | ✅ 已验证 |
| 标签页 | 右键菜单五项：关闭当前 / 关闭其他 / 移到左栏·右栏 / 刷新 / 保存；脏点；关闭确认 | ✅ 已验证（未接真实文件） |
| 分屏 | 移动语义而非复制；右栏最后一个标签挪回左栏 = 撤销分屏 | ✅ 已验证 |
| 文件树 | 任意层级嵌套，文件与文件夹同级共存 | ✅ 已验证（原型是内存假数据，生产要基于真实文件系统） |

**一条值得记下的教训**：表格点击失效的根因是 HTML 的 editing host 规则——`td` 的祖先链（`cm-content`）继承了可编辑状态，于是 `td` 不是独立 editing host，浏览器把焦点归一化到 `cm-content`。**这类问题用合成事件（`dispatchEvent`）测不出来，必须用真实鼠标输入**——后续交互验证应把「必须用真实输入」列进清单。

### 8.2 尚未验证（只能实机）

1. **中文字符手感**——真打字几天才能判断
2. **启动默认位置**——上次打开的笔记 / 空白，需实机决定
3. **Electron 下的全局快捷键**——原型没有 Electron 壳
4. **标签页系统在真实文件读写下的行为**——原型里「保存」只改内存状态，无落盘、无冲突处理

### 8.3 同步界面

> 已在原型中定形（`prototype/src/sync/`，见 [同步的用户界面](https://github.com/ziyueyijun/confidant/issues/19)）。

#### 三个部件，各答一个问题，不重叠

| 部件 | 位置 | 答什么问题 | 不放什么 |
|---|---|---|---|
| **状态栏** | 常驻屏幕底部，28px | 同步是**环境**——平时不占地方，坏了才吭声 | **不放操作**——避免同一件事有两个入口、两套样子 |
| **同步中心** | **弹窗** | 专门处理一件事，处理完就关掉 | 不放 WebDAV 配置 |
| **设置** | **从菜单进入的弹窗** | 编辑器 / 外观 / 快捷键 / 同步 / 更新 | 不放工作空间与同步操作 |
| **工作空间** | **从菜单进入的弹窗** | 打开 / 切换 / 在文件管理器里看 | 不是一项偏好，所以不在设置里 |

**状态栏默认闭嘴。** 左区只在三种情况出现：**正在进行**（同步中、待删）、**需要你处理**（冲突、自动同步失败）、**本次会话刚同步过**（「上次同步于 X 分钟前」）。其余时候整个左区是空的——「上次同步于 8 分钟前」看第二遍就没有信息量了，而它占着一个每天看几百次的位置。**重启后不显示时间**（`sessionSynced` 是会话级的），想看的人去同步中心。右区是**文档信息**（字数、行数），与应用级入口（菜单）分开。

**同步中心**两个页签（概览 / 冲突），有冲突时默认停在冲突页。概览含状态卡、待处理统计、操作区。操作区**每条命令占一整行、右侧直写后果**：

| 命令 | 呈现 |
|---|---|
| 同步 | 普通按钮，「合并两边的改动」 |
| 上传 / 下载 | 归进视觉上明显不同的**覆盖**区，执行前要求**输入确认词**，并显示具体影响范围（「将覆盖远端 N 个不同的文件」） |

**设置**按设置项分五组，**顺序就是这一份**：

| # | 分组 | 内容 |
|---|---|---|
| 1 | **编辑器** | 语法标记显示方式、源码视图、代码块（等宽字体 / 自动换行 / 行号）、编辑（Tab 宽度 / 表格渲染 / 自动保存） |
| 2 | **外观** | 主题（亮色 / 深色 / 跟随系统）、代码块配色、字体（正文字体 / 字号 / 行高）、语言 |
| 3 | **快捷键** | 常用功能清单。**第一版只列出、不允许自定义**——允许自定义要做冲突检测，那是另一块工作量 |
| 4 | **同步** | 4.1 WebDAV（连接 / 选远端目录 / 保存）、自动同步、批量删除保护 |
| 5 | **更新** | 版本、上次检查时间与结果 |

**没有「文件关联」**——用户在 Windows 设置里自己决定（§10.4）。**后续加新设置只需加一组**。

**工作空间**在菜单里而不是设置里：它管的是「打开哪个文件夹」这种应用级动作，不是一项偏好。它的面板提供【打开工作空间】【在文件管理器中打开】【切换工作空间…】。

**入口有两条**：状态栏（有话说时点它）、菜单「同步中心…」。菜单顺序：**设置 → 工作空间 → 同步中心 → 关于知己笔记**。

#### 九个必须覆盖的场景

界面必须在这些处境下都站得住（原型里逐个验证过）：刚装上、已配置（本次未同步）、本次已同步、同步中、失败、首次同步、有冲突、冲突很多、批量删除。

**前三者专门检验状态栏的显示逻辑**——「什么时候该说话」比「说什么」更容易做错。

#### 仍然只能实机验证的

**状态栏 28px、11px 中文在真机上够不够看清**——原型答不了。若偏小，把状态栏加高到 32px 即可，结构不变。

### 8.4 库外文件

**库外的 `.md` 直接正常打开、可编辑，不弹任何框。**

因为它不在库里，**没有索引、没有反向链接、不参与同步**——这件事用**界面上一处不打扰的标记如实说明**（如标签上一个小字「库外」），标记旁提供「移入库中」的动作，**用户想移才移**。

理由：拒绝打开是软件在挡路；而默默编辑一个不索引不同步的文件是隐性陷阱。标记是二者的平衡——**不妨碍任何操作，也不假装它在体系内**。

**多文件同时打开**（选中十个 `.md` 回车）：全部接受，一次批量处理，不逐个弹框。

**接收路径必须按扩展名过滤，不能按固定下标取**——Electron 文档明确警告 `second-instance` 的 `argv` 不是首次启动那个形状，且会混入 Chromium 参数。规则：**扫描 argv 里所有以 `.md` 结尾且真实存在的路径**。

**多次双击不重复启动应用**（`requestSingleInstanceLock` + `second-instance` 事件）。

## 9. 验收标准

> **用两周真实地只用它**——每天用它写东西（长笔记或短记录都算）、写一篇长笔记、**搜到过自己记的东西**、并且**两台机器之间通过 WebDAV 同步成功过一次**，全程不需要打开思源或 Typora。

**这个标准的价值在于它无法被「功能都写好了」糊弄过去**，而且它直接检验最在意的那件事：数据在你手上、软件不挡路。

拆开看，它隐含了这些必须成立的事实：

| 承诺 | 隐含要求 |
|---|---|
| 每天用它写东西 | 打开就写，不需要先选位置、先分类、先做任何准备动作 |
| 写一篇长笔记 | 中文输入法全程不出问题；所见即所得可用；标签页与分屏够用 |
| 搜到自己记的东西 | 中文检索 100% 召回；边打边搜不卡 |
| 两台机器同步成功 | 双向同步、冲突策略、锚点、凭据配置全部跑通 |
| 不开思源或 Typora | 没有一件事需要回退到旧工具 |

**「每天用它写东西」这条最容易失守**：如果打开应用后要做的第一件事是「想清楚这篇该放哪」，人就会退回 Typora。所以文件树与新建笔记的路径必须短到不需要思考。

## 10. 开工前必须定死的事

### 10.1 发布前不能改的配置

| 项 | 值 | 为什么不能改 |
|---|---|---|
| `appId` | 发布前定死 | 官方明确「发布后不能改」，且 v27 起它还决定文件关联的 ProgID。**改了就装成两个应用** |
| `publish` | 指向 GitHub Releases | 它会 `written verbatim into app-update.yml` 成为**永久更新源**。已装出去的旧版本无法自动迁移到新地址 |
| 分发形态 | NSIS per-user | 唯一同时满足「文件关联 + 自动更新」的形态 |
| `electron-builder` 版本 | 锁定 | 见 10.3 |

**`publish` 现在就定对**——将来换构建位置不用改更新源，因为源没变、只是构建位置变了。

### 10.2 分发与更新

- **NSIS per-user**（装到 `%LOCALAPPDATA%\Programs\`），**per-user 免 UAC 是安静自更新的前提**
- **不做代码签名**，不设 `forceCodeSigning: true`
- **更新包托管在 GitHub Releases**
- **发布走 GitHub Actions，打 tag 触发**（`v1.0.0` 形式）。public 仓库用标准 runner 免费；实质好处是**从全新机器构建能暴露隐藏依赖**
- **检查更新**：启动时 + 每 24 小时
- **下载完提示用户而非自动重启**——更新要重启应用，用户正在打字时不该被主动打断
- **失败必须可见**：「关于 / 更新」页显示版本与上次检查结果，失败显示角标但不弹框，错误信息要具体（「下载失败：连接超时」而非「更新失败」），下次启动自动重试
- **不做自动回滚**——要靠版本号递增发修复包；自动回滚会与 electron-updater 默认禁止降级的机制打架。**但旧版安装包不能从 Releases 删掉**——这是手动兜底成立的条件

### 10.3 ⚠️「不签名」是一个有截止日期的状态

现在（electron-builder v26 + electron-updater 6.x）未签名能自动更新（源码 `if (publisherName == null) return null` 静默跳过校验），但 master 注释明确写 **v28 会转为 fail-closed**：未签名将不再允许自动更新。

**缓解**：锁定依赖版本；升级 `electron-builder` 大版本前先确认 `win.publisherName` 的语义。

### 10.4 文件关联

- **「安装完就成为默认程序」在 Windows 10/11 上做不到**——`UCPD.sys` 过滤器驱动保护，**任何应用都做不到**。这是操作系统安全设计，不是实现问题。
- **能做到的**：安装后出现在「打开方式」里；用户下次打开 `.md` 时 Windows 主动弹一次选择框；用户在系统设置里可将其设为默认。
- **应用不提供任何「设为默认」入口。** 用户在 Windows 设置里自己决定——**应用不检测、不提示、不弹窗、不引导**。理由：这是操作系统的领域，应用插一脚只会变成打扰（用户此前明确否决过「检测并在非默认时提醒」）。
- **注册表用 electron-builder 的 `fileAssociations` 默认行为**，不维护自定义 NSIS 脚本。它写的「抢默认」那个键会被 `UserChoice` 无条件覆盖，**实际效果恰好等于「只注册为可选项」**——正是本项目要的
- **接受「可能要重启一次才生效」**——源码级缺口：NSIS 模板里只有卸载器调用 `SHChangeNotify`，安装器不调用

## 11. 已知未确证项（必须在实现时实测）

这些是调研中找不到一手来源、**只能跑一遍才知道**的。不要假设。

| 项 | 影响 | 验证方式 |
|---|---|---|
| **electron-updater 下载的安装包是否附加 MOTW、是否触发 SmartScreen** | 直接决定「自动更新会不会每次都弹警告」 | 实际跑一次完整更新流程 |
| **`If-Match` 在各大服务端的实际支持度** | RFC 4918 强烈推荐它做乐观锁，但调研到的所有实现都**不用**它（都是「先 GET 比对再 PUT」，留了一个 TOCTOU 窗口） | 若要采用，先做一次实测 |
| **文件被另一进程真正独占锁定时的行为** | 本轮未能制造真正的独占锁（Node 无直接 API）；但 `EPERM` 的处理路径已覆盖 | 实现时验证 |
| **`ENOSPC`（磁盘满）的真实行为** | 未实测（不便制造） | 实现时验证 |
| **结尾点 / 空格在 Win32 API 下的规整行为** | 实测写入「成功」，但目录列表显示为追加了 `.md`——未定论 | 若用户标题以点或空格结尾，额外验证 |
| **GitHub Releases 资源域名在国内的具体可达性** | 只确证了「GitHub 整体慢且不可靠」 | 实际发布后观察 |
