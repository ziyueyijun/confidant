## 1. 桌面壳层：Electron vs Tauri

### 结论：Electron。这是一个有硬证据的决策，不是偏好。

**Tauri 有一个直接命中笔记软件核心场景的未修复 bug。**

[tauri#15436](https://github.com/tauri-apps/tauri/issues/15436)（2026-05-24 提交，状态 open，标签 `platform: Windows` + `status: needs triage`）：在 Windows 上，当 `<textarea>` 或 **ProseMirror/TipTap contenteditable** 元素中**已有文本**时，首次聚焦会完全冻结 Windows TSF（Text Services Framework）IME。CJK 输入法无法打开候选窗口、所有按键被吞掉，直到用户输入英文字符或切换焦点。**空输入框不受影响。**

报告者验证过**所有** Win32 侧 workaround（`ImmAssociateContextEx`、`MoveFocus`、JS 侧 focus/blur 空输入框预热）**均无效**——Chromium 下一帧会覆盖。唯一的"部分 workaround"在用户首次点击同一元素时仍会复现。

即："打开一篇旧笔记继续写"这个动作会坏掉。

**旁证：最接近的同类产品正在踩这个坑。** [note-gen](https://github.com/codexu/note-gen)（12,835 stars，Tauri + 中文本地优先 Markdown + AI）的 issue 区是 IME 问题重灾区：[#936](https://github.com/codexu/note-gen/issues/936) 光标跳跃、中文变拼音；[#1035](https://github.com/codexu/note-gen/issues/1035) 配置页输入框 IME 异常（仍 open）；[#651](https://github.com/codexu/note-gen/issues/651) fcitx5 在 Wayland/Tauri 下损坏。note-gen 前端恰好混用 **CodeMirror 6 与 TipTap 3**——正是最容易踩坑的两个编辑器。

**结构性风险：上游修复拿不到。** [tao#1349](https://github.com/tauri-apps/tao/issues/1349)（2026-09-24，open）：tao 的 Windows IME 死锁修复（[tao#1215](https://github.com/tauri-apps/tao/pull/1215)，修复 `PeekMessageW` 持锁重入导致的 UI 线程永久自死锁）**已合入 tao 0.36.0**，但 Tauri 2 稳定线 `tauri-runtime-wry` 2.11.x 依赖 `tao ^0.35`，**Tauri 2 用户目前无法获得该修复**。触发场景包括 RDP 重连、**睡眠唤醒后**——主线程等待自己已持有的锁，永久死锁，只能重启应用。

**Electron 侧的事实**：Electron 44（2026-08-25）为 Chromium 152 / V8 15.2 / Node 24.18。Windows 上中文输入是 Chromium 原生能力，被 VS Code / Obsidian / Notion / **思源**长期验证。Electron 的 IME 问题主要出现在 Linux/Wayland（[electron#53175](https://github.com/electron/electron/issues/53175) 候选框跳动，已 closed as not planned），Windows 上罕见。

**头部笔记应用几乎全是 Electron**：Obsidian、Notion、Joplin、Inkdrop（[官方 showcase](https://www.electronjs.org/apps)），Logseq（其 `package.json` 依赖 electron）。

**Tauri 的真实优势（已确认，但不足以抵消）**：

| 维度 | Tauri v2 | Electron 44 |
|---|---|---|
| 引擎 | 系统 WebView（平台不一致） | 自带 Chromium 152（全平台一致） |
| 安装包 | 几 MB（+WebView2） | 80–150MB |
| 后端 | Rust | Node.js |
| 升级负担 | 跟随系统 WebView | 需跟进 Chromium 大版本（8 周一个 major，仅维护 3 个版本） |

**一处需要澄清的常见误解**：Tauri 在 Windows 上仍是 Chromium 内核（Edge WebView2），创建独立的 `msedgewebview2.exe` 多进程。**单应用内存并不必然显著低于 Electron**。实测数据点：note-gen 在 Linux 上 systemd 日志记录内存峰值约 **440–500MB**（[note-gen#603](https://github.com/codexu/note-gen/issues/603)），与 Electron 同量级。Tauri 的真实优势在"不打包引擎"和"引擎可被系统共享"。

**Tauri 的其他 Windows 边角问题**（均已查证）：原生菜单助记符（[tauri#4085](https://github.com/tauri-apps/tauri/issues/4085)）、拖放（[tauri#13761](https://github.com/tauri-apps/tauri/issues/13761)，`WebviewWindowBuilder` 的 `drag_and_drop(false)` 不生效，只有配置文件生效）、自定义全局键盘钩子在自身窗口聚焦时收不到事件（[wry#1761](https://github.com/tauri-apps/wry/issues/1761)）、E2E 自动化受 WebView2 加固破坏（[wry#1782](https://github.com/tauri-apps/wry/issues/1782)）。社区最高票功能请求之一就是"允许捆绑 Chromium"（[tauri#14963](https://github.com/tauri-apps/tauri/issues/14963)，241 reactions）——说明 WebView 碎片化是公认痛点。

## 2. 编辑器内核：CodeMirror 6 vs ProseMirror / TipTap

**CodeMirror 6 直接在 Markdown 文本上做渲染装饰**；ProseMirror/TipTap 有独立的 JSON 文档模型，需要序列化回 Markdown，而这个转换**有损**。

**旁证**：note-gen（CodeMirror 6 + TipTap 3 混用）同时踩了 IME 和 Tauri 拖放的坑，且设置了 `"dragDropEnabled": false` 作为 workaround。

**ProseMirror 路线唯一不可替代的优势**是做块级拖拽、多列排版这类富交互——而本 effort 已定文件为原子单位、不做段落级引用。

## 3. 中文全文检索（这是本项目最重要的技术空白）

### 3.1 FTS5 内置 tokenizer 只有四个，`simple` 不是其中之一

FTS5 的四个内置模块：`unicode61`（默认）、`ascii`、`porter`、`trigram`。**`simple` 是 FTS3/4 的默认 tokenizer，FTS5 没有它**。trigram 于 3.34.0（2020-12-01）加入。

### 3.2 `unicode61` 把整串汉字当成**一个** token —— 中文检索失效的根因

汉字属 Unicode `Lo` 类别，落在 token 字符范围内；而中文没有空格，"Each contiguous run of one or more token characters is considered to be a token" → **整串汉字 = 一个 token**。

**已实测**（`我喜欢知识管理`，unicode61）：

| 查询 | 结果 |
|---|---|
| fts5vocab 中的 token | 只有 `我喜欢知识管理` 一个 |
| `MATCH '知识'` | **0 行**（词在句中出现也召不回） |
| `MATCH '知识*'` | **0 行**（前缀查询救不了，token 从「我」开头） |
| `MATCH '我*'` | 1 行（只有查询词是整串 token 的**前缀**时才命中） |
| `MATCH '我喜欢知识管理'` | 1 行（必须整串完全一致） |

**结论：unicode61 下中文只能在「整串前缀」级别检索，词内检索完全不可用。**

### 3.3 `trigram` 的硬限制：**2 个汉字的查询必然失败**

trigram 把每 3 个连续字符当一个 token；"Substrings consisting of fewer than 3 unicode characters do not match any rows"。

**已实测**：

| 项 | 结果 |
|---|---|
| `MATCH '知识'`（2 字） | **0 行** |
| `MATCH '知识管'`（3 字） | 1 行 |
| `MATCH '知识*'`（2 字） | **0 行** |
| `LIKE '%知识%'` | 命中（trigram 表默认支持索引化 LIKE/GLOB），但**无法用 MATCH 排序/高亮** |
| `detail=none` | 可瘦身，但 MATCH 的 token 长度被限 ≤3 字符；短语查询报错 `fts5: phrase queries are not supported (detail!=full)` |

**索引体积（已实测，1.44 MB 随机汉字语料）**：

| 配置 | db 大小 | 相对源文本 |
|---|---|---|
| unicode61 | 4.56 MB | 3.17× |
| **trigram** | **11.21 MB** | **7.79×** |
| trigram `detail=none` | 10.23 MB | 7.11× |
| trigram `detail=none columnsize=0` | 10.19 MB | 7.08× |

**对中文的致命性**：中文最常见的查询长度就是 2 个字（「知识」「分词」「笔记」）。**trigram 对这类查询完全无效。**

### 3.4 可行路线：应用层预分词 + unicode61 + external content 表

做法：应用层先用 jieba / `Intl.Segmenter` 切词，用空格拼回（`我 喜欢 知识 管理`），再用 **unicode61** 建索引。

**已实测**：存入 `我 喜欢 知识 管理` 后，`MATCH '知识'` → 1 行；短语 `MATCH '"知识 管理"'` → 1 行；`MATCH '知*'` → 1 行。

- **优点**：零原生扩展、纯 SQL、召回接近分词质量、分词器可在应用层任意升级（换分词器 = 重建索引，**无需改数据库 schema**）。
- **缺点**：查询端**必须用同一分词器**；无法做跨词子串/单字检索（「识」单独出现搜不到）；分词错误直接丢召回；索引按词条膨胀。

**为什么这是 Electron 单人项目的最优解**：better-sqlite3 **无法纯 JS 注册 FTS5 tokenizer**（相关 PR [#944](https://github.com/WiseLibs/better-sqlite3/pull/944) 用 `Intl.Segmenter` 映射为 FTS5 tokenizer，正是为解 CJK，**至今未合并**）。替代方案要么加载 C 扩展（`wangfenjin/simple`，需与 better-sqlite3 内置 SQLite 版本兼容），要么 fork SQLite。

### 3.5 `Intl.Segmenter` 是现成的（已实测）

`Intl.Segmenter` **确实基于 ICU**，Node **16.0.0** 起可用（Chrome 87 / V8 8.7）。MDN 明确指出空白分隔的 `split(" ")` 对中文/日文/泰文/老挝文/高棉文/缅甸文都是错的。

**已实测**（Node v24, ICU 78.3）：对「我喜欢知识管理，人工智能正在改变世界。」输出 `我 / 喜欢 / 知识 / 管理 / 人工 / 智能 / 正在 / 改变 / 世界`（正确）。**吞吐约 20 MiB/s 单线程**（面向 CJK 字符）。

### 3.6 替代方案与它们的代价

| 方案 | 关键事实 |
|---|---|
| **`wangfenjin/simple`**（C++ 扩展） | 基于 cppjieba；**支持拼音全拼与首字母**（`simple_query('zhoujiel')` 与 `simple_query('zjl')` 均命中「周杰伦」）。性能：加载扩展 <2ms，首次拼音 ~500ms，首次 jieba **~4s**。**替换拼音表后已有索引中的拼音 token 不会自动重建** |
| **ICU 路线** | 官方 `ext/icu` 只提供 FTS3/4 的 `tokenize=icu zh_CN`，**FTS5 无官方 ICU tokenizer**。第三方：`cwt/fts5-icu-tokenizer`（Zig，归一化链 `NFKD; Traditional-Simplified; Lower; NFKC`）、`shcabin/sqlite-fts5-icu-tokenizer`（C++） |
| **JS 生态** | FlexSearch 有 `Charset.CJK` 预设但需自定义 tokenizer；**Lunr 无内置 CJK**；MiniSearch 默认按空格切分 → CJK 整串成一个 token，需自定义 `tokenize`；**Orama 宣称 30 种语言但无 CJK 专用说明** |
| **服务端引擎** | Meilisearch 用 charabia（**jieba-rs**，号称无需配置）；Tantivy 默认只按标点空白切分，中文需自定义 tokenizer；Typesense v0.24.0 用 **ICU（不是 jieba）** |

**公开的「trigram vs jieba 预分词 vs 自定义 tokenizer」中文横向 benchmark：未确证**（已核对 wangfenjin 实现介绍、trigram 官方文档、两个 ICU tokenizer 仓库，均无三方对比数据，或只有英文语料数字）。

### 3.7 「索引可从源文件重建」的 FTS5 机制

- **external content 表**：`content='blocks'`、`content_rowid='rowid'`，FTS5 按需回查源表取列值。**注意**：建表时**不复制既有行**，需用触发器同步；`it is the responsibility of the user to ensure that the contents of the full-text index are consistent with` 源对象。
- **`rebuild` 命令**：`INSERT INTO ft(ft) VALUES('rebuild')` → 「deletes the entire full-text index, then rebuilds it based on the contents of the table or content table」。**已实测**：清空索引后 `rebuild` 恢复命中。**contentless 表（`content=''`）不支持 rebuild**。
- **contentless-delete 表**（3.43.0+）：支持 DELETE 与 INSERT OR REPLACE。

### 3.8 中文特有需求的方案与代价

| 需求 | 现成方案 | 代价 |
|---|---|---|
| **拼音（全拼/首字母/多音字）** | `wangfenjin/simple`；`pinyin-pro`（JS，**准确率 99.846%**，gzip 157 KB，Node/Web 双支持，自动识别多音字） | 每个汉字额外产出全拼 + 首字母 token，**索引约 2–3× 膨胀**；**替换拼音表后已有 token 不会自动重建** |
| **简繁互搜** | `BYVoid/OpenCC`（词典驱动，12 种配置，Node/Python/C++ 绑定）；ICU 归一化链 `NFKD; Traditional-Simplified; Lower; NFKC` | 查询前归一化（无额外索引）或索引双写（索引翻倍） |
| **全/半角、异体字** | Unicode NFKC 归一化 | 几乎零成本 |
| **错字容错** | **FTS5 原生无模糊匹配**（trigram 只做子串）；需应用层编辑距离（SiYuan 用 `smetrics` 库） | 需要额外索引或运行时计算 |

## 4. 竞品的存储格式与组织模型

### 4.1 逐家事实

| | 原子单位 | 组织 | 格式/元数据 | 外部可否直改文件 | 中文检索 | 同步 |
|---|---|---|---|---|---|---|
| **Obsidian** | 文件 | 文件夹+链接+标签+属性 | Markdown+YAML frontmatter，配置在 `.obsidian/` | **可以（设计目标）**："Obsidian automatically refreshes your vault to keep up with any external changes" | **无官方 CJK 支持**，靠用户装分词插件 | 自带 Sync（E2EE）/ 自选网盘 / Git |
| **Logseq** | 块 | 页面+链接+标签+块引用，**无文件夹** | Markdown/Org 一页一文件；`id:: <uuid>`；**DB 版转 SQLite** | 可以但需手动 re-index | 索引需 rebuild；无公开分词信息 | Logseq Sync（付费/可自建）/ 任意文件同步（需 re-index） |
| **flomo** | 卡片 | 多级标签 `#父/子`，**无文件夹** | **纯云端**；导出**只有 HTML** | **不能**（无本地文件） | 无公开信息 | 自带云，数据在服务器 |
| **Memos** | 卡片 | `#hashtag` 层级，时间轴 | SQLite + assets；Markdown 输入 | 数据库可读 | 无公开信息 | 自托管 |
| **Notion** | 块（**页也是块**） | page 树 + 数据库 | 纯云端专有，Postgres 分片（480 逻辑分片/32 物理库） | **不能** | 无公开信息 | 自带云，**无 E2EE** |
| **Apple Notes** | note | 文件夹+智能文件夹+标签 | 本地 SQLite（`NoteStore.sqlite`），内容为 **zlib 压缩的 protobuf** | 可读，**不可安全改** | 无公开信息 | iCloud/CloudKit |
| **Bear** | note | **只有标签**（`#父/子` 嵌套），无文件夹 | 本地 SQLite；`.bear` 实为 **TextBundle 改名** | 官方：**只允许只读** | 有 CJK 搜索关键词（`@今天`、`@画像`、`@오늘`）；索引实现无公开信息 | iCloud/CloudKit，无第三方或 Git |
| **Craft** | 块 | Documents+Folders+Spaces+Collections | **默认自家云** | **不能** | 无公开信息 | 自家云 |
| **Joplin** | note | 笔记本+标签 | 本地 SQLite；**同步目标上每个 item 就是一个独立文件**（`id.md` + metadata 头部） | 可以（与同步时间戳耦合） | **明确放弃 CJK FTS**（见 4.3） | Joplin Cloud/WebDAV/S3/Dropbox/OneDrive/文件系统，**无官方 Git**，**不支持坚果云** |
| **SiYuan（思源）** | 块 | 文档树+块引用+属性视图 | **`.sy`（JSON）+ assets**；嵌入式 SQLite + FTS5 索引 | `.sy` 属自有格式 | **最好**：自研 FTS5 tokenizer 逐字分词 + 繁简归一化（见 4.4） | 官方云（8G）+ 第三方 S3/WebDAV，**明确不支持坚果云** |

**四家（Notion / Apple Notes / Bear / Craft）的全文检索与 CJK 分词实现，全部无公开技术信息**——这是本报告最一致的空白。

### 4.2 存储格式上的最佳实践共识

**共识 1：源文件是唯一真相，索引必须能完全重建。** 四条独立证据链：Obsidian 的 `Rebuild metadata cache`；Logseq 的 `Rebuild search index`；Joplin 可从同步目标文件树重建本地库；FTS5 external content 的 `rebuild` 命令（官方定义即"删除整个索引再重建"）。

**反例警示**：Logseq DB 版把真相迁进 `db.sqlite`，结果 Markdown 导出变成有损（官方："cannot capture all data in a graph"），唯一完整格式是 EDN。**一旦索引升格为真相，可迁移性就不可逆地下降。**

**共识 2：配置与用户内容必须物理分离，且配置可删可重建。** Obsidian `.obsidian/`、Logseq `logseq/`、Joplin `info.json`。经验：workspace/布局类文件应进 `.gitignore`（高频变动会污染版本历史）。

**共识 3：元数据尽量放在正文文件内（frontmatter / 属性行），而非独立数据库。** Obsidian Properties、Bear 标签在正文、Logseq `key:: value`、Joplin 同步目标的 metadata 头部——四家都在向"元数据随文件走"靠。

**共识 4：附件与正文分离，但引用可定位。** 没有一家把附件 base64 内联进 Markdown。

**共识 5：人类可读的目标标识优先于 UUID，UUID 只用于稳定寻址。** 页面级用可读文件名；块级用稳定 ID（因为块没有自然名字）。**附带教训**：Obsidian 块 ID 只能拉丁字母数字（官方："Block identifiers can only consist of Latin letters, numbers, and dashes"），Logseq 需把标题里的 `/` 编码成 `%2F` 或 `___`——**中文标题与"人类可读标识"之间的冲突并未被任何产品优雅解决。**

**共识 6：Markdown 作为互通格式被反复验证为最实用，但所有产品都承认它是有损的。** 官方损失清单：Notion callout「no Markdown equivalent」、评论仅 HTML 保留、数据库只能导当前视图；Logseq Markdown 导出不含时间戳与全部属性；Craft 纯 Markdown 丢附件；Bear 纯 Markdown 丢附件、标签降级为文本。**没有任何一家声称 Markdown 导出无损。**

**共识 7：冲突用「文件级副本 + 时间戳/文本差分」处理，而不是自动覆盖。** Joplin 冲突副本笔记本（**远端覆盖本地**，本地版复制到 Conflicts 笔记本）；Obsidian Markdown 用 **Google diff-match-patch 合并**、非 Markdown「last modified wins」、可选冲突文件（`原名 (Conflicted copy 设备名 YYYYMMDDHHMM).md`）。

**共识 8：同步后端应当是「无状态文件树」，这样网盘/Git/S3 都能当后端。** Joplin 的同步目标是一堆 `id.md` 文件；Obsidian Sync 同步的是加密后的文件。

**一条反向经验**：**不要把中文分词器参数固化在数据库 schema 里。** SiYuan 明确说「分词器参数在 CREATE VIRTUAL TABLE 时固化，切换区分大小写或区分繁简后需要重建索引」；Joplin 因为「extensions are not available in all platforms」直接放弃 CJK FTS。

**Obsidian Bases（2025 新增，值得注意）**：视图存为独立 `.base` 文件（YAML，顶层键 `filters`/`formulas`/`properties`/`summaries`/`views`）或嵌在 Markdown 代码块里。即 Obsidian 在**不引入数据库**的前提下做出了类 Notion 数据库视图——这是「纯文本 + 可重建索引」路线的一次重要验证。

### 4.3 Joplin 的检索实现（源码级事实）

**SQLite FTS4（不是 FTS5）**。中文/CJK 明确不走 FTS：`determineSearchType_` 对 `['ja','zh','ko','th']` 返回 `SEARCH_TYPE_NONLATIN_SCRIPT`，源码注释直言：

> Non-alphabetical languages aren't support by SQLite FTS (except with extensions which are not available in all platforms)

**中日韩泰均为回退式基础匹配，无分词器。** 这解释了中文用户实测「`tuite` 搜不到」。

**Joplin 的冲突处理（源码级）**：判定基于时间戳（比较 `updated_time` 与 `sync_time`）；`Note.mustHandleConflict()` **只比较 title 与 body**；被 E2EE 加密的 item 一律视为冲突。冲突时把**本地版**复制到 Conflicts 笔记本（`is_conflict=1`、`conflict_original_id` 指回原 note），**远端版覆盖本地**；新版支持基于 base 的三方 auto-merge。

**Joplin 的 WebDAV "known to work" 列表不含坚果云**（社区实践可用）。

### 4.4 思源的检索实现（源码级事实，本项目最直接的对标）

**自研 FTS5 tokenizer「siyuan」**。官方指南原文：

> The tokenizer used by SiYuan is to make Chinese search easy to use (supports single-word search), so the implementation is based on word segmentation, which means that **each Chinese character or English letter will be split into a token**

即**逐字（+逐字母）建 token**，从而单字可搜、无 OOV。

**简繁互通**：`kernel/search/hanconv_table.go` 有「2959 traditional -> simplified single-character mappings」，**繁体字归一化为简体参与索引**——同类中罕见的简繁互搜能力。

**FTS 表结构**：`blocks_fts` 是 FTS5 **external-content 虚拟表**（`content='blocks'`、`content_rowid='rowid'`），tokenize 参数：`siyuan` + `case_insensitive` / 繁简开关。注释写明「分词器参数在 CREATE VIRTUAL TABLE 时固化」。

**成本**：tokenizer 是 SQLite 的 **C 扩展**（在 go-sqlite3 的 fork 里）。外部工具无法使用——issue #16273 报错「no such tokenizer: siyuan」。

**拼音**：有实际需求但**未内置**：#10489「搜索支持拼音首字母查询」已关闭；#8396「新建文件自动加入拼音做别名」只标记为 Idea。

**同步**：官方云 + 第三方 S3/WebDAV，**明确声明「不支持坚果云」**（「第三方 WebDAV 数据同步和备份接口不含存储服务，需自行购买或搭建，不支持坚果云」）。文档警告「通过第三方同步盘进行数据同步不受支持，否则可能损坏数据」。

- [Obsidian 很好，但是搜索系統真的是災難](https://forum-zh.obsidian.md/t/topic/57396)（2026-01）：查「心理 殺人」关联的笔记返回空，「基本上都是會遇到中文切詞的問題」。

### 5.2 拼音检索——2026 年仍是空白

- SiYuan [#10489](https://github.com/siyuan-note/siyuan/issues/10489)「搜索支持拼音首字母查询」（理由：「在搜索的时候，经常需要切换输入法。感觉很不方便」）
- Obsidian 官方论坛 [Can quick switch support search note by pinyin](https://forum.obsidian.md/t/can-quick-switch-support-search-note-by-pinyin/28459)（2021 年提出，**至今无人回复**）

技术完全现成（`pinyin-pro` 准确率 99.846%；`wangfenjin/simple` 把全拼+首字母直接做进 FTS5 tokenizer）。**「输入 zs 就能找到『知识』/『只是』」在今天的中文笔记软件里没有一家原生提供。**

### 5.3 `[[链接]]` 的命名限制与中文标点正面冲突

Obsidian 官方："A string which contains the following characters may not work as a link"：`# \| ^ : %% [[ ]]`——这些在中英文混排、中文标点场景里都是高频字符。Logseq 的对策是编码（`/`→`%2F` 或 `___`），代价是**文件名被污染**（`读书___2024.md`），且改格式「point of no return」+ 全客户端 re-index。

### 5.4 中文标题的物理约束

Notion 官方承认导出时 **Windows 路径超 260 字符会失败**。中文标题往往是一整句话，按 UTF-8 每字 3 字节计，很快就逼近上限。SiYuan 的 `.sy` 文件名是文档 ID（规避了这个问题，代价是文件名不可读）；Obsidian/Logseq 用标题做文件名（可读，代价是长标题被截断或失败）。

### 5.5 IME 与编辑器：被全行业系统性忽略

Obsidian 官方论坛长期挂账：[Chinese IME Down-Arrow conflicts with search navigation](https://forum.obsidian.md/t/bug-bug-chinese-ime-down-arrow-conflicts-with-search-navigation/105167)（下箭头选候选字会同时移动搜索结果）、[Chinese IME compatibility issue with Search and Quick Switcher](https://forum.obsidian.md/t/chinese-ime-compatibility-issue-with-search-and-quick-switcher/48255)（ESC 关候选窗 vs 继续编辑）、[Ctrl+left/right/backspace to recognize non-space breaks](https://forum.obsidian.md/t/ctrl-left-right-backspace-to-recognize-non-space-breaks/25533)（**无开发者回复，未解决**）、[Global search causes software crash](https://forum.obsidian.md/t/global-search-causes-software-crash/87402)（中文输入第二个字母时崩溃）。Logseq [#12268 Can't input Chinese in LogSeq (MacOS)](https://github.com/logseq/logseq/issues/12268)（仍 open）。

**中文用户 100% 的时间在 IME 里写作。** 社区甚至写了 [cm-chs-patch](https://forum-zh.obsidian.md/t/topic/14890) 来给 Vim 模式打中文分词补丁。

### 5.6 国内可用的同步后端

- 官方 WebDAV 支持里，Joplin 的「known to work」列表**不含坚果云**；SiYuan 定价页明确写**「不支持坚果云」**。

## 6. 迁移入口的事实

- **flomo 导出只有 HTML**：「flomo 支持全局导出和设置条件导出，导出格式为 HTML，用任意浏览器即可打开」。可按标签或关键词条件导出。**无 Markdown / CSV 导出。**记录 API 与 URL Scheme（`flomo://create`）**均需 PRO 会员**。
- **Notion 导出损失（官方口径）**：非数据库页面 → `.md`；整页数据库 → **一个 CSV + 每行子页面的 `.md`**；`Create folders for subpages` 开关决定子页是否变文件夹（Windows 路径超 260 字符会失败）；**callout 只能导出为 HTML**（「there is no Markdown equivalent」）；**评论仅在 HTML 导出中保留**；数据库**只能导出当前或默认视图**，Form view 完全不能导出。
- **Notion 导出文件名 UUID 后缀**：官方文档未提。社区/迁移工具一致报告每个文件名与页面间链接带 32 位十六进制 ID，多个开源工具在代码里显式剥离。**属二手但高度一致。**
- **Notion API 2025-09-03 引入 data sources**，「Most API operations that used `database_id` now require a `data_source_id`」，且「not backwards-compatible」。

## 5.9 Windows 文件名规则（2026-09-25 实机实测）

**方法**：Node.js v24（真实 Win32 API，非 Git Bash 的 POSIX 兼容层——**后者会伪造结果**，实测中它"允许"了 `CON.md`、`星号*.md` 等 Windows 实际禁止的名字，不可信）。Windows 11。

### 禁止字符只有 9 个（半角）

`\ / : * ? " < > |` + 控制字符（U+0000–U+001F）+ 保留名（`CON` `PRN` `AUX` `NUL` `COM1`–`COM9` `LPT1`–`LPT9`）。

**实测确认禁止**：`\ / * ? " < > |` 与 U+0001 控制字符 → 均 `ENOENT`。

### ⚠️ 冒号是**静默数据损坏**，不是报错

实测：写入 `ADS测试:b.md` → 磁盘上出现的是名为 `ADS测试` 的文件，内容进入 **NTFS 备用数据流（ADS）**。回读 `ADS测试` 得到空字符串，写入的 `'hello'` 进入了名为 `b.md` 的备用流。

**后果**：文件管理器看不见那个流；**WebDAV 同步不了它**（它是流不是文件）；**内容静默消失在硬盘深处，且不报错**。这比"文件名非法"严重得多。

**注意**：`a:b` 与 `a` 在 `readdirSync` 里表现为同一个条目——**目录列表会把它当成已存在的 `a`**，这会污染任何基于路径的索引逻辑。

### 中文全角标点**全部可用**

实测全部通过：`《书名号》` `【方括号】` `（括号）` `——破折号` `、顿号` `。句号` `；分号` `：全角冒号` `？！` `“引号”` `……省略号`。

**而且半角禁止字符的全角对应也全部可用**：`：` `＊` `？` `｜` `＜` `＞` `＂` `＼` `／` —— 九种全部写入成功。

**这是本项目的关键利好**：中文写作本来就用全角标点，替换几乎是零损失的（`:` → `：` 视觉上几乎一样）。

### 文件名长度上限是 **255 个字符**，不是 85 个

实测（库根路径约 45 字符）：

| 汉字数 | 完整路径字符数 | 结果 |
|---|---|---|
| 80 | 126 | ✅ |
| 120 | 166 | ✅ |
| 200 | 246 | ✅ |
| **250** | **296** | ✅ |
| 260 | 306 | ❌ |

**推论**：限制的是 **UTF-16 字符数**（255），**不是 UTF-8 字节数**。中文标题的实际上限约 **250 个汉字**——远比 Notion 官方文档暗示的宽松（后者称 Windows 路径超 260 字符会失败）。

**但完整路径超 260 字符的通过与否取决于系统是否开启长路径支持**——实测环境开启了（296 字符的路径通过），**不能假设每台机器都开启**。库根路径长度需要在首次启动时检测。

### 大小写不敏感已确认

写入 `CaseTest.md` 后再写 `casetest.md` → 目录里只有 `CaseTest.md`，内容为后者。**第二个写入静默覆盖了第一个**。

### 未被证实但需留意

- 结尾的点或空格：实测 `结尾点.` 与 `结尾空格 ` 都写入"成功"，但目录列表显示为 `结尾点..md`（追加了 `.md`）与 `结尾空格 .md`。**Win32 API 对结尾点/空格有静默规整行为**，未在本轮定论——若用户标题以点或空格结尾，需要额外验证。
- 保留名加扩展名（`CON.md`）：本轮实测**成功**（Win32 API 对 `CON.md` 的处理与裸 `CON` 不同），但这是有历史陷阱的边角，**建议仍然避开**。

## 8. 写盘安全与异常文件（2026-09-25 实机实测）

**方法**：Node.js v24.18.0，Windows 11，真实 Win32 API。

### 8.1 原子写在 Windows 上成立

**实测**：`fs.renameSync(tmp, target)` 覆盖已存在的目标文件**成功**，内容为新的。Node 内部用 `MoveFileEx` + `MOVEFILE_REPLACE_EXISTING`，因此**POSIX 的原子写语义在 Windows 上可用**。

**这是本项目「写临时文件 → fsync → rename」策略可行的前提。**

### 8.2 fsync 的成本（100 个小文件写，每个约 300 字节）

| 方式 | 耗时 |
|---|---|
| 带 `fsyncSync` | **172ms** |
| 不带（`writeFileSync`） | **43ms** |

即每次保存多约 **1.3ms**。可接受。

**必要性**：实测未 `fsync` 时，数据可能仍在页缓存——**进程崩溃不丢，断电可能丢**。所以 rename 前必须 fsync 临时文件，否则「原子写」不成立。

### 8.3 失败模式的实际错误码

| 场景 | 错误码 |
|---|---|
| 写入时目标目录被删除 | `ENOENT` |
| rename 时目标目录不存在 | `ENOENT` |
| 读不存在的文件（外部删除竞态） | `ENOENT` |
| 把目录当文件读 | `EISDIR` |
| **只读文件（`chmod 444`）写入** | **`EPERM`** |

**⚠️ 关键发现**：Windows 上 `fs.chmodSync(p, 0o444)` **不生效**（不进 ACL），写入仍被拒并返回 `EPERM`。**因此「先检查是否可写」这个思路在 Windows 上不可靠——必须直接写、捕获错误。**

### 8.4 磁盘空间

`fs.statfsSync(path)` 可用。

**但写前预检没有意义**：预检与实际写入之间存在竞态。直接写、捕获失败。

### 8.5 二进制文件被改名成 `.md`

实测：8 字节的 PNG 头（含 `0x00`）当 utf8 解码得到 `"\u0000\u0001���PNG"`——**出现替换字符 U+FFFD，说明解码有问题**。

**可靠判据：内容含 NUL 字节（`0x00`）即视为二进制**，拒绝当笔记解析。

### 8.6 大文件读取（实测，注意与预期的偏差）

构造的「50MB」文件实际为 **153.9 MB**：

| 项 | 结果 |
|---|---|
| `readFileSync` 读取 | **823ms** |
| 字符数 | 51,300,000 |
| **按 `\n` 分割的行数** | **1 行** |

**⚠️ 这个结果暴露一个索引陷阱**：该文件无换行符，导致逐字索引会面对**一个 5130 万字符的超长 token 序列**——可能卡死或吃光内存。

**这说明「大文件限制」与「单行长度限制」是两个独立的防御**，缺一不可。

### 8.7 未被本轮证实

- **文件被另一进程独占锁定时的具体行为**：本轮的测试脚本未能真正制造独占锁（Node 无直接 API），**未实测**。归类为「需在实现时验证」，但 `EPERM` 的处理路径已由 8.3 覆盖。
- **结尾点/空格在 Win32 API 下的规整行为**（见 §5.9 末条）。
