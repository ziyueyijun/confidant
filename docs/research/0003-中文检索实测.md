## 0. 一句话结论

**预分词方案的召回缺口大到不可接受（单字查询平均召回 27–33%，跨词子串查询损失 >60%），但它有一个更好的替代品，而且比预分词更简单：逐字建 token（纯 JS，无任何 C 扩展）。**

**推荐方案：`unicode61` + 逐字空格化 + 原文列 refine。** 在 100 万字语料上，这个方案达到 **100% 召回 / 100% 精确**（783 个随机探针零误差），索引 13.99 MiB（5.18×，含原文列），查询数毫秒，增量编辑单篇 0.23ms。它**不需要** `wangfenjin/simple`——虽然该扩展实测可用（见 §5）。

这个结论推翻了票面的默认假设（「预分词 + unicode61 是可行路线」）。见 §4。

## 1. 语料：来源、规模、可复现性

**来源**：中文维基百科正文（CC BY-SA）。用 MediaWiki API 按一批常见词（历史、科学、经济、人工智能……共 50 个）搜索条目，取 `revisions/content`（wikitext），再用启发式清洗（去模板、表格、ref、内链语法、HTML 标签，保留中文占比 >35% 的段落）得到纯中文散文。

**为什么用它**：真实中文散文 → 真实的分词边界、真实的长句、真实的中英混排与标点。**不是随机汉字**。（票面明确要求）

| 项 | 值 |
|---|---|
| 条目数 | 182 |
| 切成「笔记」块（每块 400 字，模拟笔记库行粒度） | 2064 块 |
| 总字符 | 2,401,188（其中汉字 1,949,936，占 81.2%） |
| UTF-8 字节 | 6,872,122（6.55 MiB） |
| `corpus.jsonl` sha256 | `82487fb884d7df60258f71fab2acf8e9bcf4a2ad90ac102f522353ccaee0bab8` |

抓取脚本 `docs/research/spikes/fetch-corpus.js`（`node fetch-corpus.js 2400000`，约 36 秒）。

**三档规模**（票面要求 10 万 / 50 万 / 100 万字）：

| 档 | 笔记数 | 字符数 | UTF-8 字节 |
|---|---|---|---|
| 10 万 | 251 | 100,085 | 288 KB |
| 50 万 | 1,255 | 500,117 | 1.35 MiB |
| 100 万 | 2,519 | 1,000,212 | 2.70 MiB |

**⚠️ 规模说明（诚实披露）**：票面说的「100 万字」按汉字算，本语料 100 万字档对应 UTF-8 仅 2.70 MiB。真实中文笔记库若含 Markdown 标记、英文、代码、附件路径，同样字数会更大。**本报告所有「体积倍数」都以 UTF-8 字节为分母**，与 `0001` 报告 §3.3 的口径一致，可直接对比。

## 2. 必测项一：预分词（`Intl.Segmenter`）+ FTS5 `unicode61`

做法：`Intl.Segmenter('zh', {granularity:'word'})` 切词，词间用空格拼回，`CREATE VIRTUAL TABLE fts USING fts5(seg, content='docs', content_rowid='id', tokenize='unicode61')`（external content）。

**查询端**：查询词也必须用同一分词器切词。有两种构造，实测差别巨大：

| 构造 | 语义 | 例（查「中国历史」） |
|---|---|---|
| **AND** | 词间 AND，顺序无关 | `"中国" AND "历史"` |
| **短语** | 分词后的整串当一个短语，要求顺序相邻 | `"中国 历史"` |

### 2.1 索引体积与建索引耗时（实测）

| 方案 | 10 万字 | 50 万字 | 100 万字 | 内容列膨胀 |
|---|---|---|---|---|
| **preseg + unicode61** | 0.55 MiB（**2.00×**）/ 11ms | 3.50 MiB（**2.59×**）/ 62ms | 6.72 MiB（**2.49×**）/ 184ms | 1.07× |
| trigram（对照） | 2.16 MiB（7.84×）/ 37ms | 9.75 MiB（7.22×）/ 364ms | 15.68 MiB（5.81×）/ 602ms | 1.00× |

预分词是**体积最优**的方案——因为它丢掉了词内子串的位置信息。这个「优点」正是它召回缺口的原因。

### 2.2 查询延迟（实测，中位数，7 次取中位；已排除 statement 编译开销的干扰）

100 万字档：

| 查询类型 | 延迟 |
|---|---|
| 1 字 | 0.12ms |
| 2 字 | 0.12ms |
| 4 字 | 0.07ms |
| 短语 | 0.09ms |

**所有查询都在 0.1ms 量级**，规模从 10 万到 100 万字延迟只涨约 1.5×。**延迟不是问题。**

### 2.3 召回缺口（这是致命的部分）

**⚠️ ground truth 定义**：用户搜「知识」时，预期是「返回所有**包含子串**『知识』的笔记」（与 Obsidian/Everything 的直觉一致）。以此为准。

**单字查询平均召回（实测）**：

| 档 | 单字召回 |
|---|---|
| 10 万 | **33%** |
| 50 万 | **27%** |
| 100 万 | **27%** |

具体：100 万字档查「识」→ 只召回 1%（真实 196 篇）；「史」→ 33%；「国」→ 20%。**约 2/3 到 99% 的应命中笔记丢失。**

**跨词子串查询平均召回（实测）**：31%（100 万字档）。典型案例：

| 查询 | 真实命中 | 预分词召回 | 原因 |
|---|---|---|---|
| 克思 | 112 | 5% | 被切成「克/思」 |
| 共和 | 335 | 6% | 被切成「共/和」 |
| 人民共和 | 252 | 1% | 「人民/共和」跨词 |
| 第一 | 502 | 46% | |
| 中共 | 265 | 64% | |
| 部分 | 453 | 66% | |

**这正是 `0001` §5.1 里中文社区抱怨的那个 bug**（搜「大规模」找不到「扩大规模」）。

**2 字词查询平均召回 79–83%**——这是预分词表现最好的类别，但仍有约 1/5 丢失（如 100 万字档「规模」46%、「革命」64%）。

### 2.4 AND vs 短语：精度与召回不可兼得（实测，100 万字档）

| 查询 | AND 召回/精确 | 短语 召回/精确 |
|---|---|---|
| 识 | 1% / 100% | 1% / 100% |
| 克思 | 5% / 60% | 0% / 100% |
| 中国历史 | 100% / **19%** | 100% / 100% |
| 知识管理（OOV） | 100% / **0%** | 100% / 100% |

- **AND**：召回稍好，但假阳严重（「知识管理」切成分词后 AND 命中一切同时含「知识」和「管理」的文档）。
- **短语**：精确 100%，但跨词子串召回直接归零（「克思」0%）。

**两者都不能用。** 这是预分词方案的死结：它把「用户想搜的连续文本」投影到了一组词 token 上，只要用户搜的串与分词边界不重合，就永久丢失。

## 3. 必测项三：`LIKE` / trigram 兜底的代价

（先测兜底，再给结论，因为兜底方案的实测结果直接决定了 §4）

### 3.1 `LIKE` 兜底

**关键架构事实**：预分词方案用 external content 时，`content` 表的列**必须与索引内容一致**，所以 `docs.body` 存的是**分词后**的文本。在这个表上 `LIKE '%知识%'` 会因词间空格而**漏掉跨词子串**（实测 100 万字档 `LIKE '%克思%'` 在 preseg 表上返回的命中数**低于**原文表）。**要 LIKE 原文，必须另存一列原文。**

另一列原文后，`LIKE '%q%'` 全表扫的实测延迟：

| 档 | `LIKE` 全扫延迟 |
|---|---|
| 10 万 | 0.17–0.25ms |
| 50 万 | 1.07–1.46ms |
| 100 万 | 2.77–3.29ms |

100 万字档 3ms 尚可接受，但**线性增长**：1000 万字 ≈ 30ms/查询。且 `LIKE` **无法参与 FTS5 排序/高亮**，无法与主索引合并排序。

### 3.2 trigram 兜底

trigram 的硬限制（`0001` §3.3 已实测）：**2 个汉字的查询必然返回 0 行。** 本语料复现：

| 查询 | trigram MATCH |
|---|---|
| 识 / 史 / 克思 / 共和（1–2 字） | **结构性失败（0 行）** |
| 大规模 / 知识管理 / 人工智能（≥3 字） | 正常，0.03–0.06ms |
| 多词查询（「中国 历史」，含 2 字词） | **0 行** |

而 1–2 字正是中文最常见的查询长度。**trigram 无法承担中文主检索**，只能当 ≥3 字查询的补充。

## 4. ⚠️ 核心结论：预分词方案的召回缺口不可接受，最优解是**逐字索引**

这是本报告最重要的一节。

### 4.1 逐字方案：纯 JS 复刻 `simple` 扩展的机制

实测发现（推翻了一个常见假设）：**`wangfenjin/simple` 的 tokenizer 不是词级的，而是逐字的**。对「科学家研究科学」，它建出的 token 是（`fts5vocab` 实测）：

```
科 学 家 研 究 科 学   ← 每个汉字一个 token（无任何词 token）
g gu j jia jie jiu k ke x xing xue y yan   ← 每个字的拼音全拼 + 首字母
```

**这可以用纯 JS 完全复刻**：把每个汉字前后插空格，用 `unicode61` 建索引：

```js
const perchar = s => s.replace(/([㐀-鿿豈-﫿])/g, ' $1 ')
                      .replace(/ {2,}/g, ' ').trim();
// "科学家研究科学" -> "科 学 家 研 究 科 学"
```

于是 `MATCH '"知 识"'` = **相邻字短语** = **精确子串匹配**。

**⚠️ 关键细节**：空格必须插在汉字**前后**，不能只插后面。只插后面时，`26个` 会粘连成一个 token（实测），导致搜「个大」漏召回。这个 bug 我在实测中踩到并修正了（`spikes/verify.js` 有对照）。

### 4.2 逐字方案的实测数字（推荐方案：逐字 + unicode61 + 原文列 refine）

结构：`docs(id, raw, seg)`，`raw`=原文，`seg`=逐字空格化；`fts(seg, content='docs', content_rowid='id', tokenize='unicode61')`；查询命中后**回查 `docs.raw` 做 `includes` 过滤**（消除标点造成的假阳）。

| 项 | 10 万字 | 50 万字 | 100 万字 |
|---|---|---|---|
| 建索引 | 26ms | 151ms | 374ms |
| **db 体积** | 1.23 MiB（4.48×） | 7.04 MiB（5.21×） | **13.99 MiB（5.18×）** |
| 单篇编辑（增量） | 0.259ms | 0.204ms | **0.232ms** |
| 全库 `rebuild` | 10ms | 55.8ms | **116.3ms** |

**召回/精确（100 万字档，refine 后）**：

| 类别 | 召回/精确 |
|---|---|
| 单字（识/史/学/国/人） | **100% / 100%** |
| 2 字词（知识/历史/科学/经济/规模/革命） | **100% / 100%** |
| 4 字词（人工智能/世界大战/中华人民共和国/中国人民银行） | **100% / 100%** |
| 跨词子串（克思/共和/第一/部分/中共/人民共和） | **100% / 100%** |
| 短语（中国历史/大规模/知识管理） | **100% / 100%** |
| OOV（知识管理/量子纠缠笔记） | **100% / 100%** |
| 多词（「中国 历史」「北京 大学」等） | **100% / 100%** |

**查询延迟（100 万字档，含 refine 回查）**：单字 5.2ms、2 字 1.8ms、跨词 2.3ms、4 字 0.3ms、短语 0.3ms。**refine 的代价就是回查原文的那次 `includes`**；命中集大时（如「识」196 篇）稍慢，但仍在个位数毫秒。

### 4.3 精确性验证（实测，关键证据）

在 100 万字档上取 **783 个随机中文子串探针**（2–6 字），逐个比对 FTS 命中集与「原文子串」真值：

| 阶段 | 完全一致的探针 | 累计假阴 | 累计假阳 |
|---|---|---|---|
| refine **前** | 732 / 783（93.5%） | **0** | 90 |
| refine **后** | **783 / 783（100.0%）** | **0** | **0** |

- **逐字索引本身零假阴**（1683 探针的更大样本也是 0）——中文子串**一定**能命中。这是它的本质保证：子串 = 相邻的字 = 相邻的 token。
- **假阳全部来自「标点被 unicode61 丢弃」**：`开会议，决定` 里「议，决」被当成「议决」（实测样本）。分类统计：假阳分隔符 5×「，」、1×「、」、1×标点。
- **refine（回查原文 `includes`）可以 100% 消除假阳**，成本就是 §4.2 那几毫秒。

### 4.4 为什么逐字优于预分词

| | 预分词 | 逐字 |
|---|---|---|
| 中文子串召回 | 27%–83%（依查询类型） | **100%**（零假阴，实测） |
| 单字查询 | 27% | **100%** |
| 跨词子串 | 31% | **100%** |
| 精度 | AND 差 / 短语好但召回归零 | 100%（refine 后） |
| 体积（100 万字） | 6.72 MiB（2.49×） | 13.99 MiB（5.18×） |
| 查询延迟 | 0.1ms | 0.3–5ms |
| 依赖 | `Intl.Segmenter` | 无（纯 JS 正则） |
| 分词器升级成本 | **必须重建索引** | **零**（没有分词器） |

**逐字用 2× 的索引体积和几毫秒延迟，换来了 100% 召回。** 对「笔记库里搜不到自己的笔记」这个核心痛点来说，这是压倒性的划算。而且它**零依赖**、**没有分词器版本问题**（`0001` §4.2 那条反向经验「不要把分词器参数固化在 schema」被完全规避）。

### 4.5 关于「双索引取并集」

票面建议的「预分词表 + trigram 表取并集」实测**不如逐字单索引**：

| 方案（100 万字档） | 单字 | 2 字 | 跨词子串 | 体积 |
|---|---|---|---|---|
| 预分词 ∪ perchar | 100% | 100% | 100%/99% | 21.00 MiB（7.78×） |
| 预分词 ∪ trigram | **0%** | **0%** | **17%** | 25.29 MiB（9.37×） |
| **逐字单索引（推荐）** | **100%** | **100%** | **100%** | **13.99 MiB（5.18×）** |

「预分词 ∪ trigram」是**最差**的：trigram 对 1–2 字查询结构性失败，union 不能修复它，却付了 9.37× 的体积。**票面设想的双索引并集，在实测中被逐字单索引全面击败（更小、更准、更简单）。**

## 5. 必测项二：`wangfenjin/simple` 扩展

### 5.1 兼容性（票面最关键的问题）：**可行**

| 项 | 实测 |
|---|---|
| better-sqlite3 13.0.3 内置 SQLite | **3.53.4**（`select sqlite_version()`） |
| sqlite3 CLI | 3.51.1 |
| 扩展 | v0.7.1 预编译 `libsimple-windows-x64.zip` → `simple.dll` |
| **`db.loadExtension(simple.dll)`** | **成功，3ms** |
| `tokenize='simple'` | **成功** |
| `tokenize='simple_zhcn'` / `jieba` | `no such tokenizer`（**只有 `simple` 一个名字**） |

**机制**：`simple.dll` 是标准 SQLite loadable extension，**不链接任何 sqlite3 DLL**（用 `SQLITE_EXTENSION_INIT2` 的 API 指针表），DLL 导入表只有 KERNEL32/MSVCP140/VCRUNTIME140。唯一版本门禁是宿主 FTS5 `iVersion >= 2`（`src/entry.cc`），3.53.4 满足。**因此与宿主 SQLite 版本解耦，能配合 better-sqlite3 使用。这条支线不作废。**

### 5.2 首次加载的 `jieba` 耗时：**约 520ms，不是 4 秒**

`0001` §3.6 引用的「首次 jieba ~4s」被实测推翻。在干净进程里（`spikes/coldjieba.js`，两次独立运行）：

| 项 | 耗时 |
|---|---|
| `loadExtension` | **2.5ms**（官方 README 说 <2ms，吻合） |
| 首次 `simple_query`（拼音，表编译在 DLL 内） | **0.33ms**（README 说 ~500ms，**实测远快**） |
| **首次 `jieba_query`** | **521ms / 541ms** |
| 第二次 `jieba_query` | 0.17ms |

即 jieba 冷启动实测约为官方数字的 **1/8**。**但这是进程级一次性成本**：若应用启动路径上有任何一次 `jieba_query`（哪怕用户没搜中文），都要付这个 520ms。而 §4 的逐字方案**完全没有这个成本**。

### 5.3 拼音：可用，但有边界

对「周杰伦是华语流行音乐歌手」，`simple_query()` 实测命中：

| 查询 | 结果 |
|---|---|
| `zhoujiel` | 命中 |
| `zjl`（首字母） | 命中 |
| `zhoujielun`（全拼） | 命中 |
| `zhonghuarenmingongheguo`（超长全拼） | **未命中** |
| `rmghg`（超长首字母） | 命中 |

100 万字档实测：`simple_query('zhongguo')` 命中 1082 篇、`simple_query('zg')` 命中 2219 篇。**按「词级全拼 + 首字母」承诺是可靠的，不要依赖超长句级全拼。**

### 5.4 稳定性风险（需纳入验收）

上游两个 **open** issue 报告在 SQLite 3.53.x + Win11 上 `INSERT` 时进程崩溃（[#207](https://github.com/wangfenjin/simple/issues/207)、[#208](https://github.com/wangfenjin/simple/issues/208)）。**在本环境（3.53.4 + Win11）未复现**：2000 行中文插入 + 查询、20 次文件库/WAL 开闭迭代、CLI 对照，全部 exit 0。推测与特定客户端（Navicat/JVM 的 CRT 版本）相关。但两个 issue 仍 open，**若采用该扩展，建议把「进程稳定性」列入验收项**。

## 6. 必测项四：增量重建 vs 全库 rebuild

实测（单篇笔记改动 = 同一事务内 `delete` + `update` + `insert`，已预热排除页缓存一次性开销）：

| 方案 | 单篇编辑 | 全库 `rebuild` | 倍数（100 万字档） |
|---|---|---|---|
| preseg（预分词） | 0.23ms | 137ms | ~590× |
| perchar（逐字） | 0.20ms | 102ms | ~505× |
| **推荐方案（逐字+原文列）** | **0.23ms** | **116ms** | ~500× |

**结论**：单篇编辑极其便宜（亚毫秒），**完全不需要全库 rebuild**。全库 rebuild 只在「换算法/换变换函数」时需要（如改了 `perchar` 的字符类），100 万字只要 ~116ms，**1000 万字约 1.2 秒**——即使每次启动全量重建也可以接受。

**这消解了「索引必须能重建」的架构压力**：本方案里 `raw` 是真相，`seg` 是纯派生，可随时丢掉重算。

## 7. 三个候选方案的横向总表（100 万字档，实测）

## 8. 回答票面的 5 个问题

1. **基线表现**：§2。预分词索引最小（2.49×）、延迟最低（0.1ms），但**单字召回 27%、跨词子串 31%**——不可用。
2. **`wangfenjin/simple` 对比 + 兼容性**：§5。**兼容性可行**（loadExtension 成功，3ms；只有 `simple` 一个 tokenizer 名）。首次 jieba **实测 520ms，不是 4s**。质量与逐字方案相当，但引入 C 依赖与崩溃风险。
3. **预分词缺口 + 兜底代价**：§2.3 / §2.4 / §3。单字丢 73–99%；跨词子串丢 >60%。`LIKE` 兜底 3ms（100 万字）但不可排序、线性增长；trigram 对 1–2 字查询结构性失败。
4. **增量 vs rebuild**：§6。单篇 0.23ms，全库 rebuild 116ms（100 万字）。**增量极便宜，全库重建也可接受。**
5. **⚠️ 召回缺口是否不可接受 → 最优解**：**不可接受。** 最优解是**逐字索引**（§4），实测 100% 召回/精确、零 C 依赖、比票面设想的「预分词 ∪ trigram」双索引**更小更准**。

## 10. 附：几项补充实测

- **`Intl.Segmenter` 吞吐**：100 万字 292ms → **3.43M 字/s**（约 9 MiB/s）。逐字变换快 3.6×（10.6M 字/s）。
- **contentless-delete 表体积**（`content=''`, `contentless_delete=1`，只存索引不复制内容）：preseg **0.87×**、perchar **0.81×** 源文本。**比源文本还小**——但代价是**不能 `rebuild`**（实测报错 `'rebuild' may not be used with a contentless fts5 table`），且不能回查原文做 refine，与推荐方案冲突。**不推荐**。
- **中英混排**：逐字变换对英文/数字无影响（`Artificial`、`machine`、`GPT` 均原样保留、可检索），中文逐字拆开。实测 6/6 查询命中。
- **`simple` 的 `simple_query` 是逐字 AND（顺序无关）**，精度差（100 万字档 4 字词精确率 49%）；`jieba_query` 才是词级（精确率 100%）。**若用该扩展，应该用 `jieba_query`。**
